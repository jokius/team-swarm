# Fan-out на Workflow — бэкенд исполнения для режима B

Runbook **Workflow-бэкенда** режима B. Ты читаешь этот файл, потому что lead уже выбрал режим B и инструмент `Workflow` доступен (гейт выбора бэкенда и обоснование легитимности вызова `Workflow` — в `SKILL.md → «Режим B: Fan-out»`). Фолбек (agent-teams) описан там же.

Концепция fan-out общая для обоих бэкендов (владение участками, контракт-спека, гейт = сборка+тесты) — Workflow-бэкенд меняет только **чем** раздаются и сшиваются участки: один скрипт-оркестратор фанит агентов через `pipeline()` детерминированно, без team-механики (ни спавна teammates через `Agent`, ни `SendMessage`, ни idle/shutdown). Структурный вывод вместо парсинга сообщений, дешевле координация, резюмируется по `runId`.

## Что делает lead ДО запуска скрипта (раскладка, в своём контексте)

Та же раскладка, что в фолбеке, — судейская работа, её Workflow не делает. Скаут inline, потом фанишь:

1. **Режь на disjoint-участки.** Множества файлов участков **не пересекаются** — это и есть анти-гонка (в Workflow агенты пишут реально параллельно, разводит их именно непересечение наборов). Каждый участок = `{ name, files:[...], instructions }`.
2. **Выдели shared/lead-зону.** Файлы, которые трогает несколько участков (точки сборки/DI `cmd/*`, корень рефакторимого пакета, общие контракты), **не отдаются ни одному агенту** — их правит lead на интеграции, после скрипта.
3. **Напиши контракт.** `specs/contract.md` (или строкой): единые имена/расположение/сигнатуры + паттерн правки + **один эталонный пример «до/после»**. Это единственный источник правды по стилю.

## Скрипт

`sectors` и `contract` lead передаёт через `args` (реальным JSON-объектом, **не** строкой). Тот же скрипт переиспользуется на любую fan-out задачу.

```js
export const meta = {
  name: 'fanout-refactor',
  description: 'Применить контракт по N непересекающимся участкам + per-участок ревью',
  phases: [
    { title: 'Apply',  detail: 'каждый воркер правит свой участок по контракту' },
    { title: 'Review', detail: 'проверка контракта + ownership по каждому участку' },
  ],
}

const sectors  = args.sectors    // [{ name, files:[...], instructions }] — files НЕ пересекаются между участками
const CONTRACT = args.contract   // текст контракта ИЛИ путь specs/contract.md

const APPLY_SCHEMA = {
  type: 'object',
  required: ['sector', 'files_changed', 'compiles'],
  properties: {
    sector:            { type: 'string' },                            // = участок (англоязычное имя поля)
    files_changed:     { type: 'array', items: { type: 'string' } },
    compiles:          { type: 'boolean' },                            // локальная сборка участка
    shared_file_needs: { type: 'array', items: { type: 'string' } },   // нужен файл вне участка → сюда, НЕ править
    contract_gaps:     { type: 'array', items: { type: 'string' } },   // где контракт не покрыл случай
  },
}

const REVIEW_SCHEMA = {
  type: 'object',
  required: ['sector', 'verdict'],
  properties: {
    sector:  { type: 'string' },
    verdict: { type: 'string', enum: ['APPROVE', 'REJECT'] },
    issues:  { type: 'array', items: { type: 'string' } },  // плоские actionable-строки; тег [to: ...] не используем (см. ниже)
  },
}

// pipeline (НЕ parallel-барьер): участок B уже ревьюится, пока C ещё применяется.
const results = await pipeline(
  sectors,

  // Stage 1 — Apply. Первая стадия получает сам элемент.
  // .catch → ошибка агента становится null (а НЕ throw): так упавший участок не «исчезает» из пайплайна,
  // а доходит до stage 2 и честно помечается как failed (иначе lead не узнает, КАКОЙ участок не отработал).
  (s) => agent(
    [
      `Ты FAN-OUT WORKER «${s.name}». Делаешь широкую механическую правку, НЕ новую фичу.`,
      `КОНТРАКТ (закон, следуй дословно):`,
      CONTRACT,
      ``,
      `Правь ТОЛЬКО эти файлы: ${s.files.join(', ')}.`,
      `Задача по участку: ${s.instructions}`,
      ``,
      `Правила (см. role-briefs.md → «Fan-out worker brief»):`,
      `- Поведение НЕ меняй сверх паттерна контракта. Никаких «заодно почистил».`,
      `- Нужен файл вне участка — НЕ редактируй его, верни путь в shared_file_needs.`,
      `- Читать чужой код для контекста можно; ПИСАТЬ — только в свои файлы.`,
      `- Перед завершением убедись, что твой участок компилируется локально.`,
      `Верни структурой APPLY_SCHEMA.`,
    ].join('\n'),
    { label: `apply:${s.name}`, phase: 'Apply', schema: APPLY_SCHEMA }
  ).catch(() => null),

  // Stage 2 — Review. Сигнатура поздних стадий: (prevResult, originalItem, index).
  // Если apply упал/скипнут (applied == null) — НЕ спавним ревьюера впустую, отдаём маркер failed.
  (applied, s) =>
    applied == null
      ? { sector: s.name, applied: null, review: null, failed: true }
      : agent(
          [
            `Ты REVIEWER fan-out участка «${s.name}» (режим B, рефакторинг без новых тестов).`,
            `КОНТРАКТ: ${CONTRACT}`,
            `Изменённые файлы: ${(applied.files_changed || []).join(', ')}`,
            ``,
            `Проверь (см. role-briefs.md → Reviewer brief, секция Fan-out):`,
            `1. Дословное следование контракту (имена/расположение/сигнатуры/паттерн).`,
            `2. Поведение НЕ изменилось сверх согласованного паттерна.`,
            `3. Ownership: воркер не залез в чужие/shared файлы.`,
            `4. Нет оппортунистических «while I was here» правок.`,
            `Divergence → REJECT. issues — плоские actionable-строки. Тег [to: ...] НЕ используй:`,
            `в Workflow-бэкенде ролей-получателей нет, любой REJECT возвращается apply-агенту ЭТОГО участка.`,
            `Верни структурой REVIEW_SCHEMA.`,
          ].join('\n'),
          { label: `review:${s.name}`, phase: 'Review', schema: REVIEW_SCHEMA }
          // опц.: agentType под ревью — см. прозу ниже, не в шаблоне
        ).then((v) => ({ sector: s.name, applied, review: v }))
)

// НЕ фильтруем по Boolean: каждый участок должен быть представлен — упавшие как { failed: true },
// чтобы lead на интеграции увидел, КТО не отработал, а не просто недосчитался.
return results
```

Вызов (lead, его main loop):

```
Workflow({ script: "<скрипт выше>", args: { sectors, contract } })
```

> Скрипт можно сохранить как именованный workflow и звать `Workflow({ name: "fanout-refactor", args: {...} })`. Итерации — правь файл скрипта и зови с `scriptPath`/`resumeFromRunId` (см. описание инструмента Workflow).
>
> **Reviewer agentType.** Если стоит `compound-engineering` и участок того стоит — review-стадии можно дать `agentType: 'compound-engineering:review:ce-<...>'` в опциях `agent()` (например `ce-security-sentinel`). По умолчанию — дефолтный субагент.
>
> **Цена стадий.** `agent()` принимает `model` и `effort` — механическую apply-стадию можно удешевить (`effort: 'low'`), а ревью оставить на дефолте или поднять.

## Что делает lead ПОСЛЕ возврата скрипта (интеграция, в своём контексте)

Скрипт — чистый JS, файлы он не правит и общую сборку не гоняет. Это делает lead, и именно тут живёт инвариант «shared-файлы = только lead»:

1. **Сверь покрытие.** В `results` должен быть **каждый** участок из `sectors`. Любой с `failed: true` (apply упал или был скипнут) — **не применился**: обработай как перезапуск участка (см. п.5), не считай fan-out полным.
2. **Собери результаты** по успешным участкам: `applied` + `review`.
3. **Обработай `shared_file_needs[]` и shared/lead-зону.** Все запросы воркеров на чужие файлы + точки сборки/DI/корень пакета — правит **lead**, последовательно, в реальном дереве.
4. **Гейт.** Прогони **полную сборку + существующие тесты** (+ линтер, если настроен). Это гейт качества fan-out вместо RED/GREEN. ⚠️ Учти: твои собственные shared-правки (п.3) не проходили per-участок ревью — под ними только сборка и тесты; при риске прогони отдельный review субагентом через `Agent` (внутри main loop лида хука `agent()` нет — он существует только в теле Workflow-скрипта).
5. **Обработай REJECT'ы и упавшие участки:**
   - Точечный REJECT / `failed` по одному участку → догони одним `agent()` на этот участок (или мини-`Workflow` по подмножеству) с issues в промпте.
   - Системный REJECT (контракт дырявый, расходятся многие) или `contract_gaps[]` от воркеров → поправь `contract.md` и **перезапусти** скрипт по затронутым участкам.
6. **Завершение.** Никаких shutdown/роспуска команды — team не создавалась (Workflow-бэкенд команду не поднимает). Финальный отчёт: участки, файлы, что свёл lead, результат сборки/тестов, известные ограничения.

## Изоляция

**Disjoint-наборы файлов, без worktree.** Агенты пишут в разные файлы одного дерева → конфликтов нет по построению. Это тот же инвариант, что в фолбеке, просто держит его раскладка lead'а + правило ownership в промпте apply-агента (читать чужое можно, писать — только своё). Если участки нельзя порезать на непересекающиеся наборы — это сигнал, что раскладка неверная: пересмотри границы или отдай спорные файлы в shared/lead-зону, а не пытайся разрулить параллельную запись.

## Соответствие фолбеку

Концепция и инварианты те же (раскладка на disjoint, контракт, shared = только lead, гейт = сборка+тесты). Различаются только механики координации:

| Аспект | Workflow-бэкенд | Agent-teams бэкенд (фолбек) |
|---|---|---|
| Координация потока | детерминированный скрипт (`pipeline`) | план лида + `SendMessage` + `TaskStop` |
| Запрос чужого файла | `shared_file_needs[]` в выводе | `SendMessage` lead'у |
| Co-review lead'а | на интеграции (разбор `applied`+`review` после скрипта) | параллельно, по мере готовности участка |

Модификация **«без reviewer»** → выкинь stage 2 (`pipeline` из одной стадии).

## Промпты агентов

Не дублируем: apply/review промпты в скрипте = сжатая версия `role-briefs.md → Fan-out worker brief / Reviewer brief (секция Fan-out)`, **минус team-механика** (нет `SendMessage`/`TaskStop` — поток держит скрипт) и **минус тег `[to: ...]`** в вердикте (ролей-получателей тут нет). Правишь правила воркера/ревьюера в `role-briefs.md` — синхронь содержательную часть промптов сюда, но не тащи team-специфику.
