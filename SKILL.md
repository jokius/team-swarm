# Team Swarm

Скилл собирает настоящую agent team Claude Code: лид — главный поток (ты), тиммейты — именованные инстансы `Agent` в своих контекстах, связь — `SendMessage`. Сессия сама по себе неявная команда, создавать её не нужно. Два режима: A — TDD-цикл для нового поведения (tester / developer / reviewer, изоляция `tests/` vs `src/`, гейт — тесты RED→GREEN); B — fan-out для широкой механической правки (воркеры по участкам + reviewer, изоляция по владению файлами, гейт — сборка и существующие тесты). Лид раздаёт владение файлами, поэтому гонок за один файл нет.

Аргумент `install` / `setup` / `doctor` или просьба «проверь окружение», «настрой team-swarm» — это не разработка: команду не собирай, читай `install.md` и иди по нему.

## Требования среды и Preflight-гейт

Набор инструментов меняется между версиями Claude Code, и этот файл может отставать от среды (сверен с живой средой 2026-10-10, Claude Code 2.1.296; рекомендуемый минимум — 2.1.295). Поэтому первое действие скилла — живая проверка в этой сессии, а не по памяти или по прошлому разу.

Проверка:
- `Agent` — top-level; в его схеме должен быть параметр `name`. Нет `name` — не задан `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`, и любой спавн станет обычным субагентом.
- Интерактивность: `echo $CLAUDE_CODE_ENTRYPOINT` через Bash. `sdk-cli` (`-p`) и `sdk-*` (Agent SDK) — неинтерактивная сессия: `name` в схеме есть, но именованный спавн там — обычный субагент, и гард изоляции на нём не срабатывает; для Preflight это то же, что нет `name`. `cli` — терминал, проверено. Другие значения (IDE, Desktop, web) — интерактивные хосты, живьём не проверены: продолжай и покажи значение в Preflight-строке.
- `SendMessage` и `TaskStop` — у лида deferred: `ToolSearch("select:SendMessage,TaskStop")` подгружает схемы (без этого вызов падает с InputValidationError).
- `Workflow` — top-level, если не выключен (`disableWorkflows`, `CLAUDE_CODE_DISABLE_WORKFLOWS=1`).

**Первое сообщение пользователю после входа в скилл содержит Preflight-строку при любом исходе проверки; без неё никого не спавнить.** Формат:

> Preflight: Agent(name) ✅ · cli ✅ · SendMessage ✅ · Workflow ✅ → режим A (TDD), agent-teams

Строка — доказательство, что проверка выполнена, и контракт с пользователем, на чём поедем. При провале она нужнее всего.

| Результат проверки | Решение |
|---|---|
| Есть `Agent(name)`, `SendMessage`, сессия не `sdk-*` | Всё доступно. Режим A — agent-teams; режим B — Workflow, если есть, иначе agent-teams. |
| Нет `name`, сессия `sdk-*` или нет `SendMessage`, но есть `Workflow` | Режим A невозможен — скажи явно, чего нет и почему. Режим B через Workflow можно. |
| Нет `name`, сессия `sdk-*` или нет `SendMessage`, и нет `Workflow` | Команда невозможна. Скажи, чего нет, и предложи соло (честно названное соло) или починку среды: флаг, интерактивная сессия, версия, установочный режим `doctor`. Здесь спросить уместно: соло — не та работа, которую просили. |

Эвристики против самообмана:
- Не нашёл — значит нет. «Наверное, под другим именем» и «проверю по ходу» не считаются: упадёт у тиммейта в фоне, и он начнёт импровизировать.
- Провал гейта — честный разговор. Не изображай роли сам, не подменяй команду цепочкой обычных `Agent`-вызовов и не называй соло командой.
- «Задача маленькая» и «в прошлый раз работало» — не повод пропустить проверку: среда меняется между версиями.

## Жизненный цикл и имена

Один тиммейт — один этап: RED, GREEN, REVIEW или участок fan-out. Спавн → работа → финальный отчёт → `TaskStop`; следующий этап — новый спавн с чистым контекстом. Причина — изоляция: tester фичи B не несёт знаний о реализации фичи A, а пересмотренный план доходит до исполнителя целиком в новом брифе. Цена честная: каждый спавн заново собирает контекст. Итерации внутри этапа (раунды GREEN, доработка участка по замечаниям) ведёт тот же тиммейт.

- Имена уникальны на этап: `tester-<feature-id>`, `developer-<feature-id>`, `reviewer-<feature-id>`; повторный спавн роли после REJECT — суффикс раунда `-r2`, `-r3`; воркер fan-out — `worker-<sector>`, его ревьюер — `reviewer-<sector>`. Старые имена не переиспользуются. Спавн имени, которое ещё занято живым тиммейтом, молча даёт суффикс (`tester-auth` → `tester-auth-2`), бриф при этом говорит «ты — tester-auth», а сообщения на это имя уходят старому инстансу.
- После каждого спавна сверяй поле `name:` в результате `Agent` с запрошенным. Не совпало — `TaskStop` нового и разберись, кто держит имя.
- Останавливай `TaskStop` по имени и только после финального отчёта: он убивает без флаша, несообщённая работа теряется. `shutdown_request` не используй — это legacy-протокол, и он может уронить процесс лида.
- `TaskStop` не окончателен: `SendMessage` на имя остановленного воскрешает старый инстанс со всем его контекстом. Остановленным не пишут ни лид, ни пиры.
- Срочная смена курса посреди этапа — `TaskStop` и новый спавн с исправленным брифом (`-r<n>`). Догоняющий `SendMessage` занятому тиммейту может дойти только после конца его хода, когда работа уже сделана.
- Тиммейты не спавнят субагентов и не вызывают `TaskStop`, хотя оба инструмента у них есть: дети переживают `TaskStop` родителя, а вложенный агент — обходной канал к запрещённым файлам. Это строка в каждом брифе, а у `tester-*` / `developer-*` / `worker-*` гард ещё и блокирует оба вызова (раздел «Изоляция»).
- После `/resume` или рестарта лида in-process тиммейтов больше нет, а их отправки после рестарта теряются. Респавни текущий этап под новым именем.
- В конце прогона — `ListAgents` и `TaskStop` всем ещё живым тиммейтам: idle-тиммейты сами не завершаются и висят. `ListAgents` показывает и чужие сессии машины — останавливай только свои имена.

Сообщения:
- Тиммейты пишут лиду на `"main"`: такое сообщение приходит посреди хода лида, на следующем раунде инструментов. `"team-lead"` тоже работает, но доходит только на границе хода лида. Доставка автоматическая, inbox-файлы вручную не читай.
- Получатель видит превью — первую строку `message`; `summary` остаётся меткой в транскрипте отправителя и не передаётся. Поэтому первая строка — самодостаточный заголовок: «RED done for auth-login: 14 tests, all failing on stub».
- После каждого хода тиммейта лиду приходит idle-уведомление с финальным текстом хода (поле `result`). Отчёт тиммейт шлёт `SendMessage` на `"main"`, а финальный текст хода — одна строка «Reported to main.», чтобы отчёт не пришёл дважды. Если отчёта нет, сначала прочитай `result`, потом пингуй.
- Idle — это норма: тиммейт ждёт ввода, а не закончил и не упал. Не комментируй и не дёргай его, пока это не блокирует работу. Долгая тишина посреди работы — проверь, не висит ли он на permission-промпте (они всплывают у лида).
- Одно сообщение или idle-уведомление может прийти несколько раз. Обрабатывай идемпотентно: повтор отчёта не перезапускает этап и не повторяет побочных действий.

## Изоляция

Изоляцию держат три слоя: явные запреты в брифах (модели следуют им буквально), гард-хук плагина и проверка лида и reviewer'а.

Гард (`hooks/isolation-guard.*`, `PreToolUse`). Плагинные хуки срабатывают внутри тиммейтов, а `agent_type` в них — имя тиммейта (проверено живьём на 2.1.296, в доках не описано), поэтому роль гард узнаёт по префиксу имени. `tester-*`, `developer-*`, `worker-*` он всегда запрещает `Agent` и `TaskStop`. `tester-*` и `developer-*` — ещё и пути своей роли из `.team-swarm/isolation.json`: Read/Edit/Write по запретному пути, Grep/Glob, чей охват задевает запретную папку (поиск без `path` — весь проект), Bash с запретным путём в команде, а также рекурсивный поиск в Bash (`rg`, `grep -r`, `find`, `git grep`, `tree`) и `git diff` / `git show` / `git log -p` без явного пути к своей папке — такой поиск покрыл бы весь проект. Путь гард узнаёт по `/` (`rg x src/` пройдёт, `rg x src` — нет), у git — только после `--` или как `<rev>:<path>` (ref `origin/main` путём не считается). При суффиксном бане (`*_test.go`) поиск по любой папке закрыт — ищут по именам файлов. Каждая часть `;` / `&&` / `|` проверяется отдельно; отказ из-за скоупа говорит тиммейту, как перезапустить. Пути сравниваются в каноническом виде — симлинк (`t -> tests`) или другой регистр на нечувствительном к регистру диске (`Tests/`) не проходят. Карту `.team-swarm/` и файлы гарда ограниченные тиммейты менять не могут. Отказ тиммейт видит как `PreToolUse:<Tool> hook error: team-swarm isolation: …`. При карте ограниченным тиммейтам доступны только файловые, shell-, поисковые и message-инструменты (`Monitor`, `LSP`, `Artifact`, MCP-читалки обошли бы карту); нужное сверх — ключ `"allowTools"` в карте (`["mcp__plugin_playwright_playwright__*"]` для tester'а с Playwright). Модель угроз — случайные утечки и небрежный дрейф кооперативных агентов, а не агент, который целенаправленно обходит гард: переменные (`d=tests; cat $d/x`), интерпретатор со склейкой строк, вывод `npm test` или `cd tests && cat *` он не поймает. Bash — язык общего назначения; жёсткую границу дал бы только worktree без чужих файлов. Поэтому брифы и ревью остаются. Работает, только если team-swarm загружен как плагин (skills-dir или маркетплейс); у plain-скилла хуков нет — тогда изоляция держится на брифах.

Режим A — `tests/` против `src/`:
- tester не читает `src/` никаким каналом: ни Read, ни Grep/Glob, ни Bash (`cat`, `grep`, `sed`, `git show/diff/log -p`), ни через субагента; developer — то же для `tests/`. Причина: тесты пишутся вслепую по спеке и доказывают спеку, только если реализация тоже пишется вслепую.
- Фидбек по падающим тестам developer'у даёт лид: читает вывод сам и переформулирует семантически, не цитируя тесты (примеры — `tdd-cycle.md`).
- reviewer — арбитр с полным доступом. Нарушение изоляции фиксируется на ревью, фича переоткрывается.

Режим B — по владению участком: воркер пишет только в файлы своего участка, читать чужое можно (это рефакторинг, подгонять под тест нечего), общие файлы правит только лид.

Peer-сообщения — только между одновременно живыми тиммейтами, потому что написать остановленному значит воскресить его (см. выше):
- В последовательном TDD (RED закрыт до старта GREEN) живых пиров нет. tester и developer пишут только лиду (`"main"`), вопросы по спеке — тоже ему, он её владелец.
- Пиры реально есть в режиме «без TDD» (tester ∥ developer) и у воркеров fan-out. Там по умолчанию semantic peer: мелкие сверки идут без лида, и он не становится узким местом. Strict — по просьбе пользователя («strict isolation», «lead-only routing», «всё через лида», «без прямого общения»): тогда все пишут только лиду — надёжнее против подгонки под тест, но медленнее.
- Лид вписывает в каждый бриф явный список живых пиров или `none`. Список — снимок на момент спавна, поэтому участника группы живых пиров не останавливай, пока работают остальные: правь работу тем же тиммейтом, а группу останавливай целиком после финальных отчётов всех. Если замена (`-r<n>`) неизбежна — сначала напиши каждому живому пиру «`<X>` is stopped; do not message it, use main», потом `TaskStop` X.

Правила semantic peer (идут в брифы поверх файловых запретов, которые остаются базой):
1. Без цитат из файлов друг друга — ссылка словами или `path:line`.
2. Без деталей ассертов: семантика требования («после двух concurrent prompt-вызовов клиент матчит ответ к каждому по id»), а не `XCTAssertEqual(response.agentInfo.name, "first")`. Developer думает, как реализовать, а не как пройти ассерт.
3. Без учительства: на «что не так?» отвечают «требование такое-то», а не «напиши вот так».
4. Не сошлись за 3 сообщения — оба эскалируют лиду: затяжные диалоги дрейфуют за правила.
5. Спорные технические вопросы решают лид или reviewer, не peer-чат.
6. Что peer-переписка доходит до лида сама, не подтверждено — лид на это не рассчитывает: нужен её текст — просит участника продублировать на `"main"`.

## Оценка перед формированием команды

Команда — это overhead: координация, повторная сборка контекста на каждом этапе, время. Оцени задачу до спавна.

- Тривиальная (опечатка, rename, один параметр, утилита меньше 20 строк — минут на 5–10 одному): команду не поднимай. Одной строкой скажи, что делаешь соло и почему, и сделай: «Задача на пять минут — команда тут больше оркестрирует, чем работает; делаю сам. Скажи "собери команду" — подниму.»
- Средняя (одна небольшая фича, рефакторинг в пределах модуля, endpoint к существующему API): объяви дефолт и действуй в том же ходе: «Средняя задача — собираю команду; скажи "соло", если хочешь иначе.»
- Сложная (несколько связанных фич, новый модуль, нетривиальные edge cases и контракты, где изоляция tester/developer реально защищает): опубликуй план и начинай.
- Явная просьба собрать команду — не оспаривай, пользователь уже решил. Если задача при этом совсем тривиальная, отметь overhead одной строкой и собирай.

Размер: начинай с 3–5 одновременных тиммейтов (рекомендация доков agent-teams); три сфокусированных обычно лучше пяти разбросанных. Лимит для fan-out — в «Режим B».

## Выбор режима исполнения

Режим выбирает лид по природе задачи и объявляет одной строкой перед стартом.

| Сигнал в задаче | Режим |
|---|---|
| «добавь фичу», «реализуй», «построй»: новое поведение, edge cases, контракты | A (TDD) |
| «отрефактори», «мигрируй», «переименуй», «приведи к», «вынеси»: один паттерн по многим файлам без смены поведения | B (fan-out) |
| Смешанная задача | Этапы: B для механической части, A для новой. Одним режимом не пытайся. |

В режиме A ценность — изоляция tester/developer против подгонки реализации под тест, декомпозиция по фичам. В режиме B ценность — параллелизм по независимым участкам (домены, пакеты, слои), новых контрактов нет. Если сигналы противоречат друг другу и разные трактовки ведут к разной работе — задай пользователю один вопрос.

## Архитектура

- Лид — главный поток Claude Code, сам не спавнится. Ведёт план (в контексте, для длинной работы — в файле плана по правилам проекта), спавнит тиммейтов, сводит результаты. `ListAgents` и `Workflow` есть только у лида. Task-инструменты (`TaskCreate` / `TaskList` / `TaskUpdate`) на Opus 5.x появляются только с `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`; если они есть, задачи назначает лид, тиммейты их сами не берут.
- Тиммейт = `Agent` с `name`; работает в фоне. Имя команды — косметическая метка для плана, в API не участвует; подтверждения не спрашивай.
- `subagent_type`: tester, developer, воркер — `general-purpose`; reviewer — `general-purpose`, либо агент `compound-engineering` без требования отвечать только JSON: `compound-engineering:review:ce-security-sentinel`, `…:ce-performance-oracle`, `…:ce-architecture-strategist`. Персоны `ce-*-reviewer` (correctness, testing и др.) требуют JSON-only вывод в своей схеме и ломают формат вердикта. С 2.1.288 при спавне plugin-агента по имени соблюдаются его `tools` / `disallowedTools`.
- Reviewer — всегда свежий тиммейт, не форк. Вызов `Agent` с `subagent_type: "fork"` или с `isolation` тиммейта не создаёт, а форк наследует рассуждения лида, которые судье мешают оценить результат со стороны.
- Модель и effort тиммейтам не задаём: цель — задержка, а не токены, а `effort` у именованных тиммейтов всё равно игнорируется.
- Права: тиммейты стартуют в режиме прав лида, их permission-промпты всплывают у лида, фоновый агент может молча висеть на промпте. Коммиты и пуши делает только лид.
- Каналы: план — у лида; задание — в самодостаточном спавн-брифе (шаблоны в `role-briefs.md`); отчёты — `SendMessage`; артефакты — файлы (`src/`, `tests/`, `specs/` или проектные эквиваленты).

### Рекомендованные плагины

Если плагина нет, а задача от него выиграет, — одна строка рядом с планом, без вопроса, и работа идёт дальше: «Без `compound-engineering` reviewer — обычный general-purpose; поставить: … Продолжаю без него.»
- `compound-engineering` — специализированные reviewer-агенты (`ce-security-sentinel`, `ce-performance-oracle`, …): `/plugin marketplace add EveryInc/compound-engineering-plugin` → `/plugin install compound-engineering@compound-engineering-plugin`.
- `impeccable` — дизайн-проход фронтенда (раздел ниже).

`superpowers` — опциональный фолбек, не рекомендация, и строкой выше его не предлагай. TDD в скилле держит структура: изоляция tester/developer, гард и гейт лида (RED на заглушке, затем GREEN), а не плагин. Если он уже стоит, tester берёт его `test-driven-development` для дисциплины RED (`role-briefs.md`); без него ничего не теряется. Ставить только по желанию пользователя: `/plugin marketplace add obra/superpowers-marketplace` → `/plugin install superpowers@superpowers-marketplace`.

## Режим A: TDD-цикл

Подготовка: после Preflight разбей задачу на фичи; на каждую — спека `specs/<feature-id>.md` (назначение / API — модуль, путь импорта и сигнатуры / контракт / edge cases / инварианты) и скелет публичного интерфейса в `src/` с заглушкой (`panic("not implemented")` / `NotImplementedError` / `throw`). Сигнатуры tester берёт из раздела API спеки. Запиши карту изоляции для гарда — проектные пути, не обязательно `src/` / `tests/`:

```
mkdir -p .team-swarm && printf '*\n' > .team-swarm/.gitignore     # папка невидима для git
# .team-swarm/isolation.json
{ "tester": ["src/"], "developer": ["tests/"] }
```

Паттерны: `dir/` — папка от корня проекта; `*suffix` — файлы с таким окончанием (Go: `"developer": ["*_test.go"]`); иначе точный путь; `!path` — исключение для Read/Edit/Grep (на Bash не распространяется). Исключение tester'у — только для файла объявлений, который developer никогда не правит (отдельный protocol, `.pyi`, заголовок): скелет со заглушкой после GREEN содержит реализацию, его не открывай. Bash сверяется по подстроке, поэтому команда тестов или сборки роли не должна содержать её запретный путь. Go с тестами рядом с кодом: tester'у — точные пути файлов реализации (`"internal/order/order.go"`), developer'у — `"*_test.go"`. Опубликуй план и стартуй. Пошаговый runbook и примеры — `tdd-cycle.md`, брифы — `role-briefs.md`.

### RED
1. В плане: `RED: <feature-id>` в работе.
2. Спавн `tester-<feature-id>` с брифом: путь к спеке, куда класть тесты, команда тестов, пиры — `none`.
3. Дождись отчёта, прогони тесты сам: все должны падать на заглушке.
4. `TaskStop("tester-<feature-id>")`.

### GREEN
5. Спавн `developer-<feature-id>` с брифом.
6. Дождись отчёта, прогони тесты.
   - Зелёные → по желанию REFACTOR: пока developer жив, `SendMessage` ему «refactor for readability, no behavior change», затем тесты снова (красные — откат или ещё раунд GREEN).
   - Красные → до 3 раундов тем же developer'ом: читаешь вывод, переформулируешь семантически (`tdd-cycle.md`), шлёшь `SendMessage({ to: "developer-<feature-id>", message: ... })`, ждёшь отчёт, гоняешь тесты. После 3 раундов без схождения — эскалация пользователю.
7. `TaskStop("developer-<feature-id>")`.

### REVIEW
8. Спавн `reviewer-<feature-id>`: в брифе спека, список изменённых файлов и вывод последнего прогона тестов.
9. Планка REJECT: нарушение спеки или контракта; баг, дающий неверное поведение; нарушение изоляции; правка вне скоупа. Остальное — «Minor notes», закрытие не блокирует.
10. APPROVE → `TaskStop` reviewer'а, фича закрыта. Фронтенд — ещё дизайн-проход `impeccable` (раздел ниже).
11. REJECT → `TaskStop` reviewer'а и маршрут по тегу (reviewer ставит в тег имя этапа из своего брифа или `lead`). Замечания перед вставкой в бриф переформулируй по `tdd-cycle.md` → «Правила переформулировки фидбека»: у reviewer'а полный доступ, и в бриф слепого тиммейта мимо гарда легко уедет лишнее — developer'у имя теста, путь в `tests/` или ожидаемое значение, tester'у путь в `src/` или деталь реализации.
    - `[to: developer-…]` → спавн `developer-<feature-id>-r2` с замечаниями в брифе, повторный GREEN.
    - `[to: tester-…]` → спавн `tester-<feature-id>-r2`, повторный RED (код может развалиться — это TDD, GREEN будет после). Реализация уже не заглушка, поэтому в бриф — команда тестов без трейсбеков (pytest: `--tb=no -q`): трейсбек печатает исходник реализации.
    - `[to: lead]` → пересмотр спеки или плана, возврат к началу фичи.

    После правок — свежий `reviewer-<feature-id>-r2`. Максимум 3 цикла ревью, дальше — эскалация пользователю.

Пока тиммейт работает, лид не ждёт впустую: готовит спеку и скелет следующей фичи. Независимые фичи можно вести внахлёст (RED фичи B во время GREEN фичи A), если их файлы не пересекаются; пирами они друг другу не становятся. Дефолт — последовательно.

### Завершение
`ListAgents` → `TaskStop` всем, кто ещё жив; `rm -rf .team-swarm`. Финальный отчёт: что сделано, какие файлы, пройденные ревью, известные ограничения и фактическая цена прогона — сколько тиммейтов и этапов, сколько времени. Без цены триаж выше остаётся прикидкой, которую нечем поверить.

## Режим B: Fan-out (раздача по участкам)

Задача режется на независимые участки: каждый воркер владеет своим набором файлов, лид держит общий контракт, правит общие файлы и сшивает результат. Гейт качества — полная сборка и существующие тесты.

Размер. Узкое место — задержка и число агентов: сверх потолка всё встаёт в очередь. Поэтому по умолчанию не больше 5 одновременных воркеров; участков больше — укрупняй участки или давай воркеру несколько. На Workflow держись гайдлайна размера среды (сейчас «medium — keep workflows under 10 agents», меняется в `/config` → Dynamic workflow size): при двух агентах на участок это до 4 участков за прогон (пять — уже 10 агентов), иначе укрупняй или запускай батчами. Потолок параллельности Workflow — `min(16, CPU-2)`, переопределяется `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS`.

Выбор бэкенда. Workflow предпочтительнее: один скрипт раздаёт участки детерминированно и возвращает структурный вывод, без team-механики; agent-teams — фолбек.

```
Инструмент `Workflow` есть в списке инструментов?
├─ да  → Workflow-бэкенд: читай `fanout-workflow.md`, объяви «fan-out через Workflow».
└─ нет → agent-teams бэкенд (ниже). Нет и `Agent(name)` / `SendMessage` → таблица Preflight.
```

Легитимность `Workflow`. Правило инструмента: вызов легитимен, когда пользователь вызвал скилл, чьи инструкции велят вызвать Workflow. «Пользователь вызвал» значит: сам попросил команду или сворм, набрал `/team-swarm` или держит постоянную инструкцию (CLAUDE.md) работать через team-swarm. Если скилл включился без такого запроса — одна строка пользователю перед запуском Workflow. Оценку уместности команды это не отменяет. Запуск всё равно может спросить подтверждение по режиму прав; в `-p` нужен allow-rule. Просит «через команду, не через workflow» — иди в agent-teams бэкенд.

Агентам workflow никогда не шли `SendMessage`: поднимется вторая копия, которая пишет в те же файлы. Связь — только через результаты скрипта; `schema` на каждом `agent()` и восстановление через `resumeFromRunId` — в `fanout-workflow.md`.

### agent-teams бэкенд (фолбек)

Настоящая команда с планом лида и живой координацией через `SendMessage`, а не россыпь независимых `Agent`-вызовов.

Карта владения — главное правило режима, потому что два агента в одном файле затирают друг друга:
1. Один файл — один владелец. До спавна лид раскладывает участки так, что наборы файлов не пересекаются, фиксирует карту (участок → файлы → владелец) в плане и вписывает явный список файлов в бриф каждого воркера.
2. Общие файлы (точки сборки и DI вроде `cmd/*`, общие контракты, корень рефакторимого пакета) не отдаются никому. Их правит лид, последовательно, после воркеров.
3. Нужен чужой файл — воркер его не редактирует, а пишет лиду. Лид правит сам или передаёт владение и обновляет карту.
4. Воркер держит свой участок компилируемым: локальная сборка зелёная перед отчётом. Глобальную сборку держит лид на интеграции.

Контракт-спека. До спавна лид пишет `specs/contract.md` (или вкладывает в бриф): единые имена, расположение нового кода, сигнатуры, паттерн правки и один эталонный пример «до/после». Без единого ориентира параллельные воркеры разойдутся в стиле, и куски не сойдутся. Вопросы по контракту — к лиду, воркер их сам не решает.

Цикл:
1. Раскладка: участки по владению, контракт, карта, зона лида.
2. Спавн `worker-<sector>` (`Agent`): в брифе участок(и), список файлов, контракт, правило владения, команда сборки, список живых пиров.
3. Работа: воркер правит только своё по контракту и отчитывается. Мелкие сверки между воркерами — peer; контракт, архитектура и заявки на чужие файлы — к лиду.
4. Ревью по готовности: готовый участок (или пачку готовых) лид отдаёт свежему `reviewer-<sector>` и сам смотрит со-ревьюером — следование контракту, нет ли записи в чужие файлы, нет ли поведенческих изменений. Всех не ждём.
5. Интеграция: лид правит общие файлы, сшивает участки, гоняет полную сборку, существующие тесты и линтер, если настроен.
6. Расхождение с контрактом, сломанная сборка, запись в чужое → доработка тем же воркером, пока он жив; или `TaskStop` и `worker-<sector>-r2` с обновлённым брифом; или правка лидом с обновлением контракта.

Воркер живёт на свой участок или группу участков, заданную в брифе. После интеграции и APPROVE — `TaskStop`. Следующая пачка участков — новый спавн под новым именем, даже если паттерн тот же.

Завершение: участки прошли ревью и интегрированы, сборка и тесты зелёные → `ListAgents`, `TaskStop` оставшимся. Финальный отчёт: участки, файлы, общие точки, что свёл лид, результат сборки и тестов, известные ограничения, цена прогона.

## Модификации режима

- «Без TDD» → tester и developer работают на одной спеке одновременно. Изоляция файлов сохраняется; они живые пиры, поэтому действуют правила semantic peer, и каждый получает другого в списке пиров. Tester'у — команда тестов без трейсбеков (реализация пишется рядом). Останавливай обоих вместе, после отчётов обоих. Ревью — после обоих.
- «Без reviewer» → фичу закрывают зелёные тесты. Одной строкой предупреди, что без ревью качество ниже.
- Новая роль (например, architect) → дополнительный тиммейт с уникальным именем по той же схеме, бриф пишешь сам, план обновляешь.

## Дизайн-проход фронтенд-задач (impeccable)

Если задача — пользовательский фронтенд (экраны, страницы, компоненты, формы, лендинги), стадия REVIEW получает дополнительный проход плагином `impeccable`. Когда у задачи есть шаг визуальной сверки (скриншоты против макета, «дизайнер APPROVE по сверке»), проход нужен всегда. Code-review ловит логику и контракты; `impeccable` — визуальную иерархию, accessibility, адаптив, перформанс, theming, анти-паттерны.

Запускает лид — у главного потока скилл доступен надёжно, а проходу может понадобиться dev-сервер или браузер — после APPROVE reviewer'а по коду, в дополнение к нему.

Команду выбирай по тому, что проверяется:
- `critique <target>` — UX и визуал: иерархия, информационная архитектура, когнитивная нагрузка. Обычно лучший выбор для «проверяет дизайнер».
- `audit <target>` — техника: accessibility, перформанс, адаптив, theming, анти-паттерны; отчёт с severity P0–P3.
- `polish <target>` — финальный проход перед шипом: выравнивание, отступы, консистентность.
- Не уверен — `/impeccable` без аргумента покажет меню команд (там же `adapt`, `clarify`, `typeset`, `layout` и др.).

Можно несколько (например, `critique` + `audit`). Вызов: `Skill(skill: "impeccable:impeccable", args: "<command> <target>")`, где `<target>` — затронутая страница, фича или компонент.

Находки:
- Серьёзные (блокеры; у `audit` — P0/P1) → новый раунд GREEN: спавн `developer-<feature-id>-r<n>` с находками в брифе (прежний developer остановлен, писать ему нельзя), затем тесты и повторный проход.
- Мелочи (у `audit` — P2/P3) → в финальный отчёт или бэклог, закрытие фичи не блокируют.

Плагина нет — пропусти проход и один раз скажи, что для фронтенда он сильно помогает: `/plugin marketplace add pbakaus/impeccable` → `/plugin install impeccable@impeccable`.
