# Team Swarm

Собирает настоящий Claude Code agent team (swarm) через нативный agent-teams API: **сессия = одна неявная команда** (implicit-team), teammates спавнятся через `Agent` (именованные инстансы, фон — дефолт) и связаны через `SendMessage`. Team lead — сам Claude Code (главный поток), teammates — специалисты в своих контекстах. Координация: назначение = спавн-промпт (respawn-per-stage: один teammate = один этап), отчёты = `SendMessage`, план и статусы lead держит у себя (отдельного инструмента для этого нет).

Команда работает в одном из **двух режимов**, и режим выбирает lead под природу задачи (см. «Выбор режима исполнения»):
- **Режим A — TDD-цикл:** новое поведение (фичи, модули, API). Роли tester / developer / reviewer, изоляция `tests/` vs `src/`, гейт — тесты RED→GREEN.
- **Режим B — Fan-out:** широкая механическая правка существующего кода (рефакторинг, миграция, переименование по многим модулям). Роли — N доменных воркеров + reviewer, изоляция по владению участком, гейт — компиляция + существующие тесты. Исполняется на одном из двух бэкендов: **Workflow** (предпочтительно, если доступен) или **agent-teams** (фолбек) — см. «Режим B: Fan-out».

Общее для обоих: настоящая team с live-координацией через `SendMessage` (а не россыпь независимых `Agent`-вызовов), lead раздаёт владение файлами — поэтому **гонок за один файл нет**.

## Требования среды и Preflight-гейт (ОБЯЗАТЕЛЬНО, выполняется первым)

Состав инструментов менялся между версиями Claude Code, и этот документ может отставать от среды. Поэтому **первое действие скилла — всегда живой Preflight**: проверить фактическое наличие примитивов в ЭТОЙ сессии и показать результат пользователю. Не по памяти, не по этому файлу, не по прошлой сессии — только по результату проверки прямо сейчас. **Нарушение буквы гейта = нарушение его смысла** — «я примерно знаю, что там есть» не считается проверкой.

### Шаг 1. Проверка

- `Agent` и `Workflow` — top-level: смотри в своём списке инструментов.
- `SendMessage` — обычно deferred: `ToolSearch("select:SendMessage")` (заодно подгрузит схему; без этого вызов упадёт с InputValidationError).

### Шаг 2. Preflight-строка (обязательный вывод в ПЕРВОМ сообщении скилла)

Первое сообщение пользователю после входа в скилл ОБЯЗАНО содержать строку вида:

> Preflight: Agent ✅ · SendMessage ✅ · Workflow ✅ → режим A (TDD), agent-teams

Строка обязательна **при любом исходе проверки** — и когда всё есть (тогда после неё идёт план и спавн), и когда чего-то нет (тогда после неё идёт СТОП по таблице шага 3). Провал проверки не отменяет строку — наоборот, именно в провале она нужнее всего. **Нет Preflight-строки — скилл нарушен, спавнить никого нельзя.** Строка — не отчётность ради отчётности: это доказательство, что проверка реально выполнена, и явный контракт с пользователем, на чём поедем.

### Шаг 3. Решение по таблице (без импровизаций)

| Agent | SendMessage | Workflow | Решение |
|---|---|---|---|
| ✅ | ✅ | любой | Всё доступно. Режим A — agent-teams; режим B — Workflow, если есть, иначе agent-teams-фолбек. |
| ✅ | ❌ | ✅ | Доступен только режим B через Workflow. Режим A невозможен — скажи это пользователю явно. |
| ✅ | ❌ | ❌ | **СТОП.** Команда невозможна. Сообщи пользователю, предложи варианты: сделать соло (обычным способом, честно назвав это соло) или разобраться со средой (версия Claude Code, флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`). Жди ответа. |
| ❌ | — | — | **СТОП.** То же самое. |

### Что запрещено при провале Preflight

Провал гейта — это остановка и честный разговор, а не «выкрутимся». Запрещено:

- **Симулировать команду**: писать «от имени tester/reviewer» самому, изображать диалог агентов.
- **Молча деградировать в соло**, продолжая называть работу «командой» в отчёте.
- Подменять команду цепочкой обычных синхронных `Agent`-вызовов и рапортовать это как swarm.
- Ехать дальше, потому что «часть инструментов нашлась — наверное, хватит».
- Пропускать Preflight, потому что «задача маленькая», «в прошлый раз работало», «пользователь торопится».

Red flags — поймал себя на любой из этих мыслей → вернись и выполни гейт честно:

| Мысль | Реальность |
|---|---|
| «ToolSearch не нашёл, но они наверняка есть под другим именем» | Не нашёл = нет. Дальше только по таблице шага 3. |
| «Проверю по ходу, упадёт — разберусь» | Упадёт у teammate в фоне, и он начнёт импровизировать. Проверка — ДО спавна. |
| «Скилл же пишет, что инструмент существует» | Скилл отстаёт от среды. Верить только живому ToolSearch. |
| «Сделаю сам за всех, пользователь не заметит» | Заметит. Это худший исход: сломанный процесс под видом рабочего. |

## Когда срабатывает

- Фразы пользователя: "собери команду", "собрать команду", "запусти команду", "собери сворм", "team swarm", "assemble team", "подними команду" и аналоги.
- Пользователь просит команду агентов с разделением ролей для задачи разработки.

Состав и процесс зависят от выбранного режима (см. «Выбор режима исполнения»): режим A (TDD) — `lead + tester + developer + reviewer`; режим B (fan-out) — `lead + N доменных воркеров + reviewer`. Все teammates работают в фоне — это дефолт `Agent`.

Модификации: пользователь может явно попросить "без TDD" (→ режим B или параллельные RED/GREEN), "без reviewer", "добавь architect" — адаптируй.

## Оценка перед формированием команды

Прежде чем спавнить команду, lead честно оценивает, нужна ли она. Команда из 4 ролей с TDD — это overhead: больше токенов, больше координации, больше времени. Для мелких задач это оверкилл, и лучше об этом прямо сказать.

### Классификация задачи

**Тривиальная** — один teammate был бы избыточен, не то что команда:
- Фикс опечатки, rename переменной, формат кода.
- Добавить один параметр в существующую функцию.
- Написать одну маленькую утилитную функцию (< 20 строк) в существующем файле.
- Что-то, что решается за 5-10 минут одному.

**Средняя** — команда поможет, но single-agent тоже справится:
- Одна небольшая фича (одна функция/класс с несколькими методами).
- Рефакторинг в пределах одного модуля.
- Добавить endpoint к существующему API.

**Сложная** — команда явно уместна:
- Несколько связанных фич, которые имеет смысл декомпозировать.
- Новый модуль/подсистема с нуля.
- Задача с нетривиальными edge cases и контрактами, где изоляция tester/developer реально защищает от cheating.
- Любая задача, где пользователь уже сам сказал "хочу команду" явно — не второгадываем, он решил.

### Что делать по каждой категории

**Тривиальная** — **не поднимай команду автоматически**. Ответь пользователю прямо:

> «Задача тривиальная (фикс опечатки / one-liner / ~5 минут работы). Команду из 4 агентов с TDD разворачивать — оверкилл: больше overhead на оркестрацию, чем самой работы. Предлагаю сделать один. Если всё-таки хочешь команду — скажи, подниму.»

Затем сделай задачу сам. Если пользователь переспросит "всё равно собери команду" — подними без вопросов.

**Средняя** — предупреди, но поднимай по умолчанию:

> «Задача средней сложности. Могу сделать один — быстрее и дешевле. Или собрать команду с TDD — медленнее, но надёжнее и с review. Что предпочитаешь? (по умолчанию соберу команду, раз ты просил)»

Если пользователь не уточнил — поднимай команду.

**Сложная** — поднимай команду без лишних вопросов, просто опубликуй план и начинай.

### Исключение: явный запрос пользователя

Если пользователь сказал "собери команду" и явно описал задачу или контекст, где он уже принял решение — **не оспаривай**. Исключение — если задача настолько тривиальна, что отказаться было бы странно (например, "собери команду, чтобы исправить опечатку в README"). Тогда всё равно коротко отметь overhead, но если настаивает — поднимай.

## Выбор режима исполнения

Команда умеет работать в двух режимах. **Режим выбирает lead** под природу задачи — это не дефолт и не выбор пользователя. Lead определяет сам и одной строкой объявляет выбор перед стартом. Пользователь может стопнуть и обсудить, но молча угадывать его предпочтение не нужно — нужно прочитать задачу и решить.

**Режим A — TDD-цикл.** Создаём *новое поведение*: фичи, модули, endpoints, бизнес-логику с контрактами и edge cases. Изоляция tester/developer защищает от подгонки реализации под тест. Декомпозиция — по фичам. Гейт — тесты (RED→GREEN→REVIEW). Раздел «Режим A: TDD-цикл».

**Режим B — Fan-out (раздача по участкам).** Меняем *существующее поведение* широко и механически: рефакторинг по многим модулям, миграция, переименование, внедрение одного паттерна в N мест, починка вызовов после смены API. Поведение не меняется (или меняется предсказуемо одинаково везде), новых контрактов нет. Ценность — параллелизм по независимым участкам, а не TDD-дисциплина. Декомпозиция — по участкам владения (домены / пакеты / слои). Гейт — компиляция + существующие тесты зелёные. Раздел «Режим B: Fan-out».

| Сигнал в задаче | Режим |
|---|---|
| «добавь фичу», «реализуй», «построй», новое поведение, есть edge cases и контракты | A (TDD) |
| «отрефактори», «мигрируй», «переименуй», «приведи к», «вынеси», правка одного паттерна по многим файлам без смены поведения | B (fan-out) |
| Смешанная: часть — новое поведение, часть — широкая механическая правка | Раздели на этапы: B для механической части, A для новой. Не пытайся одним режимом. |

Когда сигналы противоречивы и режим неочевиден — **задай пользователю один вопрос**, а не выбирай вслепую. Дешевле уточнить, чем развернуть не тот режим.

## Выбор модели под роль

Третье решение лида в цепочке: нужна ли команда → какой режим → **на каких моделях**.

Дефолт `Agent` — наследование модели лида. Это не решение, а его отсутствие: лид сидит на топовой модели, и вся команда едет на ней же, включая роли, где это не добавляет ни капли качества. **Модель выбирает lead, отдельно под каждую роль, и ставит `model` в спавне явно.** Не поставил — значит выстрелил моделью лида по механической работе и даже не заметил.

Проверено живьём (2026-09-02, лид на Opus 5): параметр реально применяется, а не игнорируется — `model: "haiku"` дал `claude-haiku-4-5-20251001`, `model: "fable"` дал `claude-fable-5-1`. Алиасы `Agent`: `haiku`, `sonnet`, `opus`, `fable`.

**Планка = цена ошибки роли, а не объём её работы.** Роль, которая много печатает по готовому контракту, — дешёвая. Роль, чья ошибка проедет дальше незамеченной, — дорогая. Объём текста не значит ничего.

| Роль | Дефолт | Вниз, когда | Вверх, когда |
|---|---|---|---|
| `tester` (RED) | `sonnet` | спека уже перечисляет все кейсы явно, от tester'а требуется транскрипция, а не поиск edge cases → `haiku` | контракт с нетривиальными инвариантами: конкурентность, протоколы, числовые границы, порядок событий → `opus` |
| `developer` (GREEN) | `sonnet` | GREEN — обвязка поверх готовой библиотеки или заполнение skeleton'а по сигнатурам → `haiku` | алгоритмика, конкурентность, нетривиальные структуры данных, перф-критичный путь → `opus` |
| `reviewer` | **уровень лида** (= `model` не указывать) | практически никогда: арбитр — последний фильтр перед пользователем, экономия здесь окупается ровно один раз | некуда, если лид уже на топе; если лид на `sonnet`, а цена бага высокая (деньги, доступы, миграции данных) → `opus` |
| fan-out worker (apply) | `haiku` | это и есть дефолт: контракт дословный, есть эталонный пример «до/после» | участок требует локальных решений, а не подстановки по образцу → `sonnet` |
| fan-out reviewer | `sonnet` | — | участок трогает безопасность, деньги, конкурентность, миграции → `opus` |

Колонки «вниз»/«вверх» — исключения, а не чек-лист: ни один триггер явно не сработал (типичный случай — прикладная логика без конкурентности и без готовой библиотеки под задачу) → берётся дефолт из второй колонки, и это законченный ответ, а не повод домысливать. Не видно из задачи, насколько дорога ошибка — не гадай: дефолт плюс строка объявления, пользователь поправит, если ставки выше, чем выглядят.

Fan-out воркеру `opus` не нужен почти никогда. Если участку он действительно нужен — это сигнал, что участок нарезан неправильно либо задача вообще не fan-out, а режим A.

**Ловушки — все ловятся только чтением, ни одна не падает с ошибкой:**

- `subagent_type: "fork"` **игнорирует** `model` — форк всегда идёт на модели лида. Для reviewer'а-форка писать `model` бессмысленно: это не ошибка, просто ничего не произойдёт. Нужен reviewer на другой модели — спавни обычным `general-purpose`, не форком.
- У `Agent` **нет** параметра `effort`. Он есть только у `agent()` внутри Workflow-скрипта (см. `fanout-workflow.md`). Не передавай `effort` в `Agent` — схема его не примет.
- Модель живого teammate не меняется на лету — только respawn. При respawn-per-stage это бесплатно: смена модели и так происходит на границе этапа.
- «Уровень лида» — единственный случай, когда `model` правильно **не** указывать: наследование и есть нужный результат. Во всех остальных ролях отсутствие `model` — это не «как у лида по решению», а необъявленный выбор по умолчанию. И относится это **только к reviewer'у режима A**: у fan-out reviewer'а свой дефолт (`sonnet`) и он ставится явно — рефлекс «ревьюеру model не пишем», принесённый из TDD, молча вернёт наследование модели лида, ровно то сползание, против которого весь раздел.
- `fable` доступна и работает, но в рубрике не используется. Ставь её осознанно под конкретную причину, а не «за компанию».

**Эскалация моделью вместо жалобы пользователю.** Дешёвая модель не сошлась — это ещё не повод идти к пользователю. Порядок: роль исчерпала отведённые раунды (3 в TDD-цикле, REJECT по участку в fan-out) → **respawn той же роли на ступень выше**, с теми же входными данными и замечаниями в брифе → и только если не сошлось и там — эскалация пользователю. Одна ступень за раз, не больше одного подъёма на этап, подъём называется в отчёте («developer поднят `sonnet` → `opus` на фиче X»). **Роль уже на верхней ступени (`opus`) — шаг пропускается, идёшь сразу к пользователю.** `fable` ступенью выше `opus` не является и в лестницу не подставляется. Работает и в обратную сторону: роль на `opus`, которая этап за этапом делает работу уровня `sonnet`, на следующем этапе спускается.

**Объявление выбора.** До первого спавна, рядом с планом и Preflight-строкой, одной строкой:

> Модели: tester `sonnet` · developer `sonnet` · reviewer `opus` (= lead) — логика прямая, планку держим на ревью.

Строка нужна ровно затем, зачем Preflight: выбор становится видимым и оспоримым до того, как за него заплачено. Пользователь назвал модель сам — не спорь и не выбирай, ставь названную.

Не превращай рубрику в ритуал: это одно решение на команду, а не исследование на каждого teammate. Сомневаешься между дефолтом и ступенью **вниз** — бери нижнюю: недобор чинится одним respawn'ом, перебор не чинится ничем. Сомневаешься, сработал ли триггер **вверх** (то есть спор идёт про цену ошибки, а не про экономию) — бери верхнюю: там правило ровно обратное.

## Архитектура

**Lead** — главный поток Claude Code (ты сам). Не spawn'ится как teammate. Ведёт план, спавнит teammates, синтезирует результаты.

**Teammates** — параллельные Claude instance'ы, спавнятся через `Agent` с `name`:
- `tester` (subagent_type: `general-purpose`)
- `developer` (subagent_type: `general-purpose`)
- `reviewer` (subagent_type: `general-purpose`, либо `compound-engineering:review:*` если установлен)

Фон — дефолт `Agent`: teammates работают параллельно, а не синхронными вызовами.

Полезные опции `Agent`, о которых стоит помнить:
- `subagent_type: "fork"` — форк наследует полный контекст lead'а. Уместен **только для `reviewer`** (он и так арбитр с полным доступом, а форк экономит ему пересбор контекста). Для `tester` и `developer` — категорически нет: форк принесёт им ровно то знание, от которого их изолируют.
- `model` — модель teammate'а. Ставится **всегда и явно**, по рубрике из «Выбор модели под роль»; без него teammate наследует модель лида. С `subagent_type: "fork"` игнорируется — форк всегда на модели лида.

Состав живой команды lead смотрит через `ListAgents` (кто запущен, кто busy/idle). У teammates этого инструмента нет — он только у lead'а.

> **Спавн и остановка.** Спавн тиммейта — инструмент `Agent` (с `name`), остановка — `TaskStop` по имени. Вывод teammate'а читать не нужно: он сам отчитывается через `SendMessage`. План и статусы lead ведёт сам, назначения передаёт в спавн-промптах.

> **Idle — это норма.** После каждого хода teammate уходит в idle и шлёт автоматическое idle-уведомление. Idle ≠ «закончил» и ≠ «упал» — он просто ждёт ввода. Не комментируй idle и не дёргай по нему, пока это реально не блокирует работу. Сообщения от teammates **доставляются автоматически** новыми ходами — lead не читает inbox-файлы вручную.

### Именование team'ы

В implicit-team модели отдельного объекта команды нет, поэтому «имя команды» теперь чисто косметическая метка для твоего плана и отчёта — в API оно нигде не используется. Важны **имена teammates** (`tester`/`developer`/`reviewer` и т.п.) — по ним идёт `SendMessage` и `TaskStop`. Если пользователь дал имя команде — используй как метку; подтверждения дефолтного имени не спрашивай.

### Рекомендованные плагины

Два плагина сильно усиливают работу команды. Оба опциональны — команда работает и без них, но с ними лучше.

**`superpowers`** (основной рекомендуемый) — фреймворк composable skills: `test-driven-development` (enforced RED/GREEN/REFACTOR с delete-code-if-cheating), `writing-plans`, `subagent-driven-development`, `systematic-debugging` (4-фазный root cause process), `verification-before-completion`, и другие. Наш skill отвечает за swarm-оркестрацию и изоляцию ролей; `superpowers` даёт сами рабочие методологии для teammates. Вместе — хорошая связка.
- Установка: `/plugin marketplace add obra/superpowers-marketplace` → `/plugin install superpowers@superpowers-marketplace`.
- Когда teammate запущен и `superpowers` доступен, он сам подхватит релевантные skills. Мы явно скажем ему это делать в brief'е (см. `role-briefs.md`).

**`compound-engineering`** (опциональный) — набор специализированных review-агентов (`ce-security-sentinel`, `ce-performance-oracle`, `ce-architecture-strategist`, `ce-code-simplicity-reviewer` и т.д.).
- Установка: `/plugin install compound-engineering`.
- Если установлен — `reviewer` запускается с подходящим `subagent_type` (например, `compound-engineering:review:ce-security-sentinel` для задач с безопасностью). Без плагина — `general-purpose`.

### Как Lead учитывает плагины

Перед спавном команды, в первом сообщении пользователю рядом с планом, коротко упомяни недостающие плагины, если задача от них выиграет. Пример:

> «Для этой задачи сильно помогли бы два плагина:
> - `superpowers` (обязательно рекомендую, без него teammates работают без enforced TDD/debug-методологий): `/plugin marketplace add obra/superpowers-marketplace` → `/plugin install superpowers@superpowers-marketplace`
> - `compound-engineering` (опционально, для более глубоких review): `/plugin install compound-engineering`
>
> Можно продолжить без них — просто качество ниже. Что предпочитаешь?»

Не блокируй работу. Если пользователь не отреагировал или попросил продолжить — поднимай команду без плагинов. Это предложение, не требование.

**Коммуникация:**
- **План лида** — список фич/этапов, зависимости, статусы. Отдельного инструмента для него нет: lead ведёт план у себя (в контексте, а для длинной многофазной работы — в файле плана, как принято в проекте). Teammates его не видят и не трогают — им всё нужное приходит в спавн-промпте.
- **Спавн-промпт** — назначение задачи: teammate спавнится под конкретный этап/участок, и его задача целиком описана в его брифе.
- **Сообщения** (через `SendMessage`, всегда по `name` получателя; lead адресуется как `"team-lead"` или `"main"`) — отчёты и переписка между агентами. Доставка автоматическая.
- **Файловая система** — код в `src/`, тесты в `tests/`, спеки в `specs/` (или проектные эквиваленты).

**Ключевое**: teammates общаются peer-to-peer (tester может написать developer'у напрямую через `SendMessage`). Это мощно, но опасно для изоляции — см. раздел «Изоляция».

## Изоляция ролей (критично)

> Этот раздел описывает изоляцию **режима A (TDD)** — по `tests/` vs `src/`. В режиме B (fan-out) изоляция другая — **по владению участком** (см. «Режим B: Fan-out → Изоляция в fan-out»). Правила semantic peer ниже общие для обоих режимов.

В swarm mode teammates могут общаться напрямую. Это значит, что **изоляция не обеспечивается архитектурой — её обеспечивают промпты**. Lead несёт ответственность за три вещи:

**1. File-level ограничения в промптах.**
В промпте tester'а явно: «не читай файлы в `src/`». В промпте developer'а: «не читай файлы в `tests/`». Это первая линия и она работает В ЛЮБОМ режиме общения.

**2. Peer messaging — два режима, выбирает пользователь.**

- **Semantic peer (default).** Tester ↔ developer могут писать друг другу напрямую (`SendMessage`) с жёсткими правилами (см. ниже). Lead подключается только на спорных моментах. Лучше пропускная способность, меньше bottleneck'а на lead'е.

- **Strict (opt-in).** Активируется фразами пользователя «strict isolation», «lead-only routing», «без прямого общения», «всё через lead» при создании команды. Tester и developer пишут только team-lead'у; lead посредничает каждый запрос. Безопаснее против TDD-cheating, но медленнее.

**3. Lead как посредник feedback'а.**
Когда developer'у нужен feedback о падающих тестах — lead читает вывод сам, **переформулирует семантически** (не цитируя тесты) и передаёт developer'у через `SendMessage`. Примеры переформулировок — в `tdd-cycle.md`.

Reviewer — единственный, у кого полный доступ (read всё, write всем). Он арбитр.

### Правила semantic peer mode (если активирован)

Эти правила прописываются в каждый brief tester'а и developer'а **дополнительно** к file-level ограничениям. Сами файлы по-прежнему изолированы: tester не читает `src/`, developer не читает `tests/` — это база, она остаётся.

1. **Запрет на цитирование файлов друг друга.** Tester не вставляет в сообщение строки из тестов, developer — из реализации. Если хочешь сослаться на место — описывай словами или через `path:line`, без вставки содержимого.

2. **Запрет на детали ассертов.** Tester описывает **семантику требования** («после двух concurrent prompt-вызовов клиент должен корректно сматчить response к каждому по id»), но **не** конкретный ассерт («XCTAssertEqual response.agentInfo.name, \"first\"»). Это сохраняет TDD-spirit: developer думает «как реализовать», а не «как пройти ассерт».

3. **Запрет на «учительство».** Tester не предлагает developer'у решения и архитектуру. Если спросили «что не так?» — отвечай «требование такое-то», не «надо вот так-то написать».

4. **Lead видит peer DM.** Когда teammate шлёт DM другому teammate, его краткое резюме автоматически приходит lead'у в idle-уведомлении отправителя. Lead читает между делом, без обязанности отвечать; вмешивается, если видит нарушение правил 1-3. (Если нужен полный текст — попроси участника продублировать через `SendMessage to=team-lead`.)

5. **Эскалация на 3-м сообщении.** Если peer-разговор не сошёлся за 3 сообщения подряд — оба эскалируют на lead. Затяжные диалоги — частый источник дрейфа за пределы правил.

6. **Reviewer всё ещё арбитр.** Спорные технические вопросы → reviewer (full access), не peer-чат.

7. **Файловые ограничения первичны.** Если кто-то всё-таки прочитает запрещённые файлы (Read tool на tests/ от developer'а) — это нарушение, фиксируется leadom при review и фича переоткрывается.

Когда сомневаешься — идёшь к lead. Semantic peer — про скорость на простых вопросах, не про обход TDD-discipline.

## Жизненный цикл teammates

**Принцип: respawn-per-stage, а не long-lived.**

Teammate спавнится под конкретный этап (RED, GREEN, REVIEW), отрабатывает его, шлёт финальный отчёт — и lead останавливает его через `TaskStop(<name>)`. На следующий этап lead спавнит новый инстанс (`Agent`) с чистым контекстом.

Зачем так:
- **Чистый контекст.** На RED-фазу feature-B tester приходит без памяти о feature-A. Нет риска, что он случайно потащит знание о реализации из прошлого этапа.
- **Пересмотренные промпты.** Если план пересмотрен (например, reviewer зарезал спеку), новый teammate получает обновлённый brief с нуля.
- **Предсказуемость.** Нет длинных разговоров, которые могут «разморозить» изоляцию со временем.

Цена — немного больше токенов на spawn и shutdown. Для TDD-цикла это приемлемо.

Исключение: **итерации внутри одного этапа** (например, 3 раунда GREEN при падающих тестах) — это тот же teammate, не respawn. Respawn происходит только между RED → GREEN → REVIEW (и между фичами).

## Режим A: TDD-цикл

### Инициализация сессии (один раз)

Явного создания команды не требуется — сессия уже является неявной командой (implicit-team). После Preflight-гейта зафиксируй у себя план (этапы RED/GREEN/REVIEW на каждую фичу), **выбери модели ролей** по «Выбор модели под роль» и объяви их одной строкой рядом с планом — и спавнь teammates (`Agent` с `name` и явным `model`).

Декомпозировать задачу пользователя на фичи. Для каждой фичи — детальная спека в `specs/<feature-id>.md` (Назначение / API / Контракт / Edge cases / Инварианты). Skeleton публичного интерфейса (сигнатуры + тело-заглушка: `panic("not implemented")` / `NotImplementedError` / `throw`) — в `src/`.

### Для каждой фичи

#### RED

1. Отметить в плане этап `"RED: <feature-id>"` как in progress.
2. Spawn tester (`Agent`, явный `model`) с brief'ом из `role-briefs.md` — задача (какую спеку читать, куда класть тесты) целиком в брифе.
3. Дождаться отчёта tester'а (придёт автоматически через `SendMessage`).
4. Прогнать тесты — ожидание: все падают (на заглушке). Red достигнут.
5. **`TaskStop("tester")`** — этап закрыт, tester больше не нужен.

#### GREEN

6. Отметить `"GREEN: <feature-id>"` в плане.
7. Spawn developer (`Agent`, новый инстанс, чистый контекст, явный `model`) — задача в брифе.
8. Дождаться отчёта.
9. Прогнать тесты.
   - **Зелёные** → переход к шагу 11 (REVIEW через respawn reviewer'а).
   - **Красные** → итерация (до 3 раундов, **без** respawn'а developer'а):
     1. Lead читает вывод тестов.
     2. Lead **переформулирует** проблему семантически (правила в `tdd-cycle.md`).
     3. `SendMessage({ to: "developer", message: "<semantic feedback>" })`.
     4. Developer правит, шлёт новый отчёт → lead прогоняет тесты.

   После 3 раундов без схождения — **сначала эскалация моделью**: `TaskStop("developer")` → respawn на ступень выше с той же спекой и накопленным feedback'ом. Не сошлось и там (или developer уже был на верхней ступени) — эскалация пользователю. См. «Выбор модели под роль → Эскалация моделью».

10. **`TaskStop("developer")`**.

#### REFACTOR (опционально)

Если код зелёный, но грязный — **до остановки developer'а** с шага 10, отправь ему `SendMessage`: "refactor for readability, no behavior change". После изменений прогнать тесты. Зелёные — ок. Красные — откат или новая GREEN-итерация.

Затем `TaskStop("developer")`.

#### REVIEW

11. Отметить `"REVIEW: <feature-id>"` в плане.
12. Spawn reviewer (`Agent`, новый инстанс; `model` — уровень лида, т.е. не указывается). Отправь reviewer'у через `SendMessage` вывод последнего прогона тестов.
13. Дождаться verdict.

**APPROVE** → `TaskStop("reviewer")`, закрыть фичу в плане, следующая фича (новый RED → новый spawn tester'а).

> **Фронтенд-задачи:** после APPROVE по коду — прогнать дизайн-проход `impeccable` подходящей командой (`critique` / `audit` / `polish` / …; см. «Дизайн-проход фронтенд-задач (impeccable)»). Серьёзные находки → обратно в GREEN перед закрытием фичи.

**REJECT** → маршрутизация:
- `[to: developer]` → `TaskStop("reviewer")`, spawn developer'а заново с REJECT-комментариями в брифе, повторный GREEN.
- `[to: tester]` → `TaskStop("reviewer")`, spawn tester'а заново с REJECT-комментариями, повторный RED. Код развалится — ок, это TDD, повторный GREEN будет после.
- `[to: lead]` → `TaskStop("reviewer")`, пересмотр спеки/плана, возврат к началу фичи.

После правок — новый spawn reviewer'а на повторный REVIEW. Максимум 3 цикла review. После — эскалация пользователю: эскалация моделью здесь не применяется, reviewer и так на уровне лида, поднимать некуда. Три круга review — это симптом дырявой спеки, а не слабой модели.

### Завершение сессии

Когда все фичи DONE, все teammate'ы уже остановлены (respawn-per-stage гарантирует, что в конце никого не висит). Роспуск команды не требуется — она живёт с сессией и исчезает вместе с ней. Убедись лишь, что каждому отработавшему teammate был сделан `TaskStop` — иначе он висит фоном и тратит ресурсы.

Финальный отчёт пользователю: что сделано, какие файлы, пройденные review, известные ограничения.

## Режим B: Fan-out (раздача по участкам)

Fan-out режется на независимые **участки**: каждый воркер владеет своим и правит только свои файлы, lead держит общий контракт и сшивает результат. Концепция (владение, контракт-спека, гейт = сборка+тесты) общая — но **исполнить** её можно одним из двух бэкендов:

- **Workflow-бэкенд (предпочтительно).** Один скрипт-оркестратор фанит агентов через `pipeline()` детерминированно, без team-механики. Полный runbook — в **`fanout-workflow.md`**.
- **agent-teams бэкенд (фолбек).** Настоящая team с планом лида и координацией через `SendMessage` — описан ниже.

**Гейт выбора бэкенда** (lead уже выбрал режим B, теперь выбирает бэкенд):

```
Инструмент `Workflow` есть в списке инструментов? (top-level, не deferred)
├─ да  → Workflow-бэкенд → читай `fanout-workflow.md`, объяви «fan-out через Workflow» и иди туда.
└─ нет → agent-teams бэкенд (раздел ниже). Нет и `SendMessage` → см. «Требования среды».
```

**Легитимность вызова `Workflow`.** Правило инструмента разрешает его, когда «пользователь вызвал скилл, чьи инструкции велят вызвать Workflow» — team-swarm ровно такой, так что опт-ин обеспечен самим фактом вызова скилла: отдельно спрашивать пользователя или произносить `ultracode` не нужно. Но это снимает только техническое разрешение на инструмент — **оценку уместности команды** (раздел «Оценка перед формированием команды»: тривиальная/средняя задача → предупреди/спроси) делай как обычно. Если пользователь явно просит «через команду / не через workflow» — уважь и иди в фолбек.

### agent-teams бэкенд (фолбек)

Параллельная команда без TDD-цикла. Задача режется на независимые **участки**, каждый воркер владеет своим и правит только свои файлы. Lead держит общий контракт и сшивает результат. Это **не** россыпь независимых `Agent`-вызовов — это настоящая team с live-координацией через `SendMessage`, и именно поэтому здесь **нет гонок за файлы**.

### Анти-гонка: карта владения (главное правило режима)

Гонка за один файл — главный риск параллельной работы: два агента редактируют один файл, второй затирает первого. В fan-out это закрывается **владением (ownership)**, а не надеждой:

1. **Один файл — один владелец.** До спавна lead раскладывает участки так, что множества файлов не пересекаются, и фиксирует карту владения у себя в плане; **явный список файлов/директорий** каждого участка попадает в бриф его воркера. Пересечений нет по построению, а не по удаче.
2. **Общие файлы — только lead.** Файлы, которые трогает несколько участков (точки сборки/DI вроде `cmd/*`, общие контракты, корень рефакторимого пакета), **не отдаются никому**. Их правит lead — последовательно, после воркеров.
3. **Нужен чужой файл — не лезь, пиши lead.** Воркер, упёршийся в файл вне своего участка, **не редактирует** его, а шлёт `SendMessage` lead'у. Lead правит сам или передаёт владение и обновляет карту. Это ровно то, чего не умеют fire-and-forget агенты, — поэтому и нужна настоящая команда.
4. **Воркер держит свой участок компилируемым.** Локальная сборка своего пакета/модуля зелёная перед рапортом `completed`. Глобальную сборку держит lead на интеграции.

### Контракт-спека (защита от рассинхрона)

Параллельные воркеры разойдутся в стиле, если им не задать единый ориентир, и куски не сойдутся при сборке. До спавна lead пишет короткий **контракт** в `specs/contract.md` (или вкладывает в каждый brief): единые имена, расположение нового кода, сигнатуры, паттерн правки + **один эталонный пример «до/после»**. Все воркеры следуют ему дословно. Контракт — единственный источник правды по стилю; вопросы по нему идут к lead, не решаются воркером самостоятельно.

### Цикл

1. **Раскладка.** Lead анализирует, режет на участки по владению, пишет контракт-спеку, фиксирует карту (участок → файлы → владелец) в своём плане. Заранее помечает общие файлы как «зона lead».
2. **Спавн.** Lead спавнит воркеров (`Agent`) — каждому его участок + ссылку на контракт + правило ownership (из `role-briefs.md`) + явный `model` (дефолт fan-out: воркеры `haiku`, reviewer `sonnet` — см. «Выбор модели под роль»). Работают параллельно.
3. **Работа.** Воркер правит только свои файлы по контракту, держит локальную компиляцию, рапортует `completed`. Мелкие сверки между воркерами — peer (`SendMessage`); контрактные/архитектурные вопросы и заявки на чужие файлы — к lead.
4. **Ревью по готовности.** Как только участок готов — lead отдаёт его reviewer'у (reviewer подключается, когда есть что ревьюить, как в режиме A) и **сам смотрит независимым взглядом со-ревьюера**: следование контракту, не залез ли воркер в чужие файлы, нет ли поведенческих изменений там, где их быть не должно. Не ждём всех — ревьюим по мере поступления.
5. **Интеграция.** Lead правит общие файлы (точки сборки/DI, корень пакета), сшивает участки, гоняет **полную сборку + существующие тесты** — это гейт качества fan-out (вместо RED/GREEN). Линтер, если настроен.
6. **Расхождение** (с контрактом, сломанная сборка, залез в чужое) → возврат воркеру с уточнением (respawn с обновлённым brief'ом, **на ступень выше** по модели, если воркер уже не справился на дешёвой) или правка lead'ом + обновление контракта.

### Изоляция в fan-out

Изоляция здесь — **по владению участком**, а не по `tests/` vs `src/` (как в режиме A). File-level правило в каждом brief'е: воркер **пишет** только в файлы своего участка. Читать чужой код для понимания контекста можно (это рефакторинг, подгонять под тест нечего) — но писать в чужое нельзя. Reviewer и lead — полный доступ. Правила semantic peer (запрет учительства, эскалация на 3-м сообщении, lead видит DM) действуют и здесь.

### Жизненный цикл воркеров

Respawn-per-участок: воркер живёт на свой участок; после интеграции и APPROVE — `TaskStop(<worker-name>)`. Итерации внутри участка (доделать после замечаний) — тот же воркер, без respawn. Если участки воркера однородны (тот же паттерн правки) — инстанс можно переиспользовать на следующий участок; при смене характера работы — respawn с чистым контекстом.

### Завершение

Когда все участки прошли review и интегрированы, полная сборка и тесты зелёные — `TaskStop` оставшимся воркерам и reviewer'у. Роспуск команды не требуется — она живёт с сессией. Финальный отчёт: какие участки, какие файлы, общие точки, что свёл lead, результат сборки/тестов, известные ограничения.

## Модификации режима

- **"Без TDD"** → RED и GREEN идут параллельно (tester и developer на одной спеке одновременно, без зависимости). Изоляция сохраняется. Review после того, как оба закончили.
- **"Без reviewer"** → не спавни reviewer, закрывай фичу по факту зелёных тестов. Предупреди пользователя, что качество без reviewer'а ниже.
- **Добавить роль (например, architect)** → спавни дополнительного teammate, добавь его brief в сессию, обнови свой план.

## Дизайн-проход фронтенд-задач (impeccable)

Если задача — **пользовательский фронтенд** (экраны, страницы, компоненты, формы, лендинги — любой видимый UI), стадия REVIEW получает **дополнительный** проход через плагин `impeccable`. Он **обязателен**, когда у задачи есть шаг визуальной/дизайнерской сверки (скриншоты против макета, «дизайнер APPROVE по сверке»). Code-review ловит логику и контракты; `impeccable` ловит то, что code-review не видит, — визуальную иерархию, accessibility, адаптив, перформанс, theming, анти-паттерны.

**Кто и когда.** Запускает **lead** (у главного потока надёжно доступен skill, а проходу может понадобиться dev-сервер/браузер) на стадии REVIEW, **после** того как `reviewer` вернул APPROVE по коду. Не вместо code-review, а в дополнение.

**Какую команду — по ситуации.** Не зашивайся в одну; выбери самую подходящую под то, что проверяет дизайнер:
- **`critique <target>`** — UX/визуальное ревью (иерархия, информационная архитектура, когнитивная нагрузка, эмоция). Обычно лучший выбор для «проверяет дизайнер».
- **`audit <target>`** — техническое качество: accessibility, перформанс, адаптив, theming, анти-паттерны. Scored-отчёт с severity **P0–P3**.
- **`polish <target>`** — финальный проход перед шипом (выравнивание, отступы, консистентность, микродетали).
- Не уверен, какая нужна → запусти `/impeccable` без аргумента: покажет меню всех команд по категориям, выбери оттуда (там же точечные `adapt`/`clarify`/`typeset`/`layout` и др.).

Можно прогнать и несколько (например, `critique` + `audit`), если ревью покрывает и визуал, и технику. Вызов: `/impeccable <command> <target>` (через Skill-tool — `Skill(skill: "impeccable:impeccable", args: "<command> <target>")`), где `<target>` — затронутая страница / фича / компонент.

**Маршрутизация находок:**
- **Серьёзные** (блокеры; у `audit` это P0/P1) → новые GREEN-фиксы: `SendMessage` developer'у в рамках текущей фичи (или respawn по циклу REVIEW → GREEN), затем повторный прогон тестов + повторный проход.
- **Мелочи / nice-to-have** (у `audit` это P2/P3) → в финальный отчёт пользователю или бэклог; закрытие фичи не блокируют.

**Если плагина нет.** `impeccable` опционален — без него скилл не падает: пропусти проход, но один раз сообщи пользователю, что для фронтенд-задач он сильно помогает (`/plugin marketplace add pbakaus/impeccable` → `/plugin install impeccable@impeccable`).
