# Swarm Primitives — cheat sheet для team-swarm паттерна

Быстрая справка по нативному agent-teams API Claude Code (модель implicit-team: сессия сама является командой, лид — главный поток). Не полная документация — только то, что использует этот скилл.

> Сверено с живой средой 2026-10-10, Claude Code 2.1.296. Живьём проверено: набор инструментов лида и заспавненного тиммейта (ToolSearch с обеих сторон), схема `Agent` у лида, формат результата спавна, доставка `SendMessage` на `"main"` и на `"team-lead"`, форма idle-уведомления, `TaskStop`, `SendMessage` на имя остановленного тиммейта, спавн занятого имени и того же имени после `TaskStop`, плагинные хуки внутри тиммейтов (интерактивная сессия с `--plugin-dir`, затем E2E на самом team-swarm). Остальное — по докам, CHANGELOG и issues (номера указаны). Минимальная рекомендуемая версия — 2.1.295 (фикс первого `SendMessage` у тиммейтов; plugin-типы по имени — с 2.1.288). Если что-то отсюда не находится в твоей сессии — верь ToolSearch и схеме инструмента, а не файлу, и действуй по Preflight из SKILL.md.

Содержание: Включение · Спавн · Имена · Остановка · Сообщения · Idle · Координация · ListAgents и зачистка · Права, resume, MCP · Хуки внутри тиммейтов · Что не является тиммейтом · Типичные ошибки

## Включение

- Нужен `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`. Без него у `Agent` нет параметра `name`, и любой спавн — обычный субагент без team-механики (в открытом #100613 `name` не было и при выставленном флаге). Поэтому Preflight проверяет именно наличие `name` в схеме `Agent`.
- Команды работают только в интерактивной сессии: в `-p` и в Agent SDK тиммейты не спавнятся. Параметр `name` там в схеме есть, но именованный спавн становится обычным субагентом, и гард изоляции на нём не срабатывает (для субагента `agent_type` — его тип, а не имя). Отличить: `echo $CLAUDE_CODE_ENTRYPOINT` — `sdk-cli` под `-p`, `sdk-*` в SDK; `cli` в терминале (проверено); IDE, Desktop и web ставят свои значения — это интерактивные хосты, живьём не проверены.
- Создавать команду не надо — сразу спавнь тиммейтов. Одна команда на сессию, вложенных команд нет.

## Спавн

```
Agent({
  name: "tester-parser",              // уникальное имя этапа, см. «Имена»
  subagent_type: "general-purpose",   // дефолт; reviewer — ещё ce-агент без JSON-only вывода (SKILL.md → «Архитектура»)
  description: "RED for parser",
  prompt: "<бриф из role-briefs.md — задача целиком внутри>"
})
```

Результат содержит `agent_id: a<name>-<hex>` (формат с 2.1.290; раньше был `<name>@session-...`) и `name: <name>`. Сверь `name:` с запрошенным. Не совпало — имя было занято живым тиммейтом, и новый получил суффикс (`tester-parser-2`): останови новый (`TaskStop`) и разберись, почему жив старый.

Не передавай:
- `model` и `effort`. Модель не понижаем: цель команды — задержка, а не токены. `effort` у именованных тиммейтов всё равно игнорируется (#100701).
- `subagent_type: "fork"` и `isolation` — такой вызов создаёт не тиммейта (см. «Что не является тиммейтом»).
- `mode`, `team_name` — deprecated, игнорируются.
- `run_in_background`. В интерактивной сессии с fork mode (дефолт) этого параметра в схеме `Agent` нет — субагенты и так в фоне; в `-p` он есть, но команд там всё равно не бывает. У тиммейта `run_in_background: true` падает (доки agent-teams, Limitations).

Plugin-тип по имени (например, reviewer из `compound-engineering`) применяется к именованному спавну с 2.1.288; на более старых версиях молча спавнился generic-тиммейт.

## Имена

**Каждый спавн получает новое уникальное имя, а к имени остановленного тиммейта больше не обращаемся.**

Схема:
- `tester-<feature-id>`, `developer-<feature-id>`, `reviewer-<feature-id>` — режим A;
- повторный спавн той же роли на той же фиче — суффикс `-r2`, `-r3` (`developer-parser-r2`);
- `worker-<sector>` и `reviewer-<sector>` — воркер fan-out и ревьюер его участка.

Почему так — два живых наблюдения:
- Спавн имени, занятого живым тиммейтом, молча даёт суффикс (`probe` → `probe-2`). Бриф при этом говорит «ты — probe», а сообщения на `probe` уходят старому.
- `SendMessage` на имя остановленного тиммейта воскрешает старый инстанс со всем прежним контекстом («resumed it ... with 64 prior messages»).

Уникальные имена снимают обе ловушки. После `TaskStop` имя освобождается, и спавн с ним получает чистый контекст, но полагаться на это незачем.

Адресуем всегда по `name`. `agent_id` нужен, только если у агента нет имени или имя занял более новый агент.

## Остановка

```
TaskStop({ task_id: "tester-parser" })   // имя или agent_id
```

Ответ `task_type: "in_process_teammate"` — остановлен именно тиммейт. Что важно знать:
- Убивает сразу, без флаша (#98442): несообщённая работа теряется. Останавливай после финального отчёта.
- Не окончателен: следующий `SendMessage` на это имя — от лида или от пира — вернёт старый инстанс (см. «Имена»).
- Дети не останавливаются: субагенты, которых заспавнил тиммейт, переживают его `TaskStop`, и ни результат, ни уведомление о них не говорят (#95138). У тиммейтов есть и `Agent`, и `TaskStop`, поэтому брифы запрещают им спавнить субагентов и вызывать `TaskStop`.
- Порядок смены этапа: финальный отчёт → `TaskStop` старого → спавн следующего.

`shutdown_request` не используем: это legacy-протокол, и одобрение shutdown in-process тиммейтом может уронить процесс лида (#96226). Только `TaskStop`.

## Сообщения

### Загрузка схемы
У лида `SendMessage` и `TaskStop` — deferred: один раз перед первым вызовом `ToolSearch("select:SendMessage,TaskStop")`, иначе InputValidationError. У тиммейтов на 2.1.295+ `SendMessage` top-level; в брифах ToolSearch остаётся только фолбеком «если `SendMessage` не вызывается».

### Отправка
```
SendMessage({
  to: "developer-parser",
  summary: "feedback round 1",   // метка в транскрипте отправителя, получателю не передаётся
  message: "Feedback round 1 for parser: empty input and partial last page\n<семантический фидбек>"
})
```
Получатель видит превью — первую строку `message`. Поэтому первая строка — самодостаточный заголовок («RED done for parser: 14 tests, all failing on stub»). Broadcast нет: нескольким адресатам — по сообщению каждому. Содержимое файлов в сообщение не вставляй, давай пути и `path:line`: в auto mode классификатор может не пропустить такое сообщение как утечку данных (проверено живьём).

### Адрес лида
Оба адреса доставляют, но по-разному (проверено живьём):
- `to: "main"` — приходит лиду посреди его хода, на следующем раунде инструментов. Брифы используют его: лид видит отчёт, даже пока сам занят.
- `to: "team-lead"` — пишется в inbox команды и доходит только на границе хода лида.

### Доставка
- Автоматическая: лид не читает inbox-файлы и не поллит.
- Занятому тиммейту в интерактивной сессии сообщение может прийти только после конца его хода (#99111), то есть когда работа уже сделана. Срочная смена курса посреди этапа — `TaskStop` и спавн с исправленным брифом под новым именем (`-r<n>`), а не догоняющий `SendMessage`.
- Сообщение, попавшее на переход busy → idle, может «припарковаться»: тиммейт уходит в idle, не отреагировав (#82858). Если на follow-up пришло только idle-уведомление — короткий пинг, а не весь бриф заново.
- Дубли: одно сообщение или idle-уведомление может прийти несколько раз (#92244), а сообщения до компакта лида — всплыть через полчаса-час (#97798). Обрабатывай идемпотентно: повтор (тот же `from` и `timestamp` или тот же текст) не перезапускает этап; на дубль от уже остановленного этапа не отвечай — ответ его воскресит.

### Peer-сообщения
Только между одновременно живыми тиммейтами. Лид вписывает в бриф явный список живых пиров (или «none»): написать остановленному пиру — значит воскресить его.

## Idle

После каждого хода тиммейт уходит в idle, и лид получает уведомление с финальным текстом хода (поле `result`, с 2.1.251):
```
{"type":"idle_notification","from":"tester-parser","timestamp":...,"idleReason":"available","result":"Reported to main."}
```
- Idle ≠ «закончил» и ≠ «упал»: тиммейт ждёт ввода, следующий `SendMessage` его будит. Уведомления приходят после каждого хода, поэтому сами по себе ответа не требуют — не комментируй и не дёргай тиммейта, пока это не блокирует работу.
- Отчёт тиммейт шлёт `SendMessage` на `"main"`, а финальным текстом хода оставляет одну строку («Reported to main.»), чтобы лид не получал отчёт дважды. Отчёта нет — сначала прочитай `result` последнего idle-уведомления, потом пингуй.
- Что резюме peer-DM приходит лиду в idle-уведомлении отправителя, живьём не подтверждено — не рассчитывай на это. Нужен текст peer-переписки — попроси участника продублировать его на `"main"`.
- Idle-тиммейты сами не умирают и висят, пока их не остановят (#89515).

## Координация

- План и статусы — у лида: в контексте, для длинной работы — в файле плана проекта. Task-инструменты (`TaskCreate` / `TaskList` / `TaskUpdate`) не удалены, а гейтятся моделью: на Opus 5.x их нет без `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`. Если они в сессии есть, тиммейты задачи сами не берут — назначение по-прежнему через бриф.
- Назначение — спавн-бриф: тиммейт спавнится под ровно один этап или участок, полностью описанный в брифе.
- Статус — `SendMessage`-отчёт на `"main"` («сделал X, файлы Y, команда и её результат, вопросы Z»). Структурированные JSON-статусы не нужны.
- Зависимости — секвенированием: лид не спавнит GREEN, пока RED не закрыт.

## ListAgents и зачистка

`ListAgents` есть только у лида: у тиммейтов нет ни его, ни `Workflow` (проверено живьём). Он показывает тиммейтов (`name [ref] · type · running/idle`) и вдобавок все peer-сессии машины и Remote Control — свои среди них только строки с именами этого прогона.

В конце прогона: `ListAgents` → `TaskStop` каждого ещё живого тиммейта этого прогона. Соседние сессии не трогай.

## Права, resume, MCP

- Права. Тиммейты стартуют в режиме прав лида (кроме `dontAsk`; `--dangerously-skip-permissions` распространяется на всех). Их permission-промпты всплывают в сессии лида и ждут пользователя, а фоновый агент может молча висеть на промпте часами, не подавая сигнала (#99887). Коммиты и пуши делает только лид; на `ask`-правила как на страховку от фоновых агентов не полагайся — они могут не сработать (#100454).
- Resume. In-process тиммейты не переживают `/resume`, `/rewind` и рестарт лида; их отправки в inbox после рестарта теряются (#100013). После resume — респавн текущего этапа под новым именем.
- MCP. Именованный тиммейт получает набор инструментов на момент начала текущего хода лида: MCP-сервер, который ещё подключается, он не увидит до конца жизни (#98953). Роли, которым нужен MCP (например, tester с Playwright), не спавнь в самом первом ходе сессии.

## Хуки внутри тиммейтов

Проверено живьём на 2.1.296; в доках для тиммейтов не описано — может поменяться.
- Плагинные хуки (`PreToolUse`, `SubagentStart`) срабатывают и внутри in-process тиммейтов. Во входе есть `agent_id` (`a<name>-<hex>`) и `agent_type`.
- Для тиммейта `agent_type` — это его имя (`tester-parser`), а не тип агента, и для `general-purpose`, и для plugin-типа. На этом стоит гард team-swarm: роль — префикс имени.
- `permissionDecision: "deny"` из плагинного `PreToolUse` тиммейт соблюдает: Read, Bash, `Agent` и `SendMessage` блокируются, он видит `PreToolUse:<Tool> hook error: <reason>`.
- Plugin-агент с `disallowedTools: Agent, TaskStop` даёт тиммейта вообще без `Agent`. Team-swarm на это не опирается: гард по имени работает и для `general-purpose`.
- В auto mode классификатор режет межагентные сообщения с содержимым файлов («Data Exfiltration»): отчёты ссылаются на `path:line`, а не вставляют код.
- Hook input приходит компактным JSON (`"agent_type":"tester-x"` без пробелов) — на этом держится дешёвый shell-префильтр `hooks/isolation-guard.sh` (6 мс против ~30 мс у node на каждый вызов инструмента).

## Что не является тиммейтом

- `Agent` с `subagent_type: "fork"` или с `isolation` создаёт обычного субагента, а не тиммейта (доки agent-teams). Форк вдобавок наследует весь контекст и рассуждения лида: для tester/developer это пробой изоляции, для судьи — потеря взгляда со стороны. Reviewer — всегда свежий тиммейт (`general-purpose` или ce-агент без JSON-only вывода — SKILL.md → «Архитектура»).
- `isolation: "worktree"` — аварийный выход fan-out, когда участки не режутся на непересекающиеся файлы. Это субагент; его worktree по умолчанию ветвится от `origin/<default>`, а не от локального HEAD (меняет `worktree.baseRef: "head"`), так что незапушенные коммиты лида он не увидит. После этапа — `git worktree list` и прибрать. Подробнее — в `fanout-workflow.md`.
- Агенты `Workflow` — тоже не тиммейты. `SendMessage` им не шлём: поднимется вторая копия, пишущая в те же файлы (#93797).

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `InputValidationError` на `SendMessage` / `TaskStop` у лида | Схема deferred-инструмента не загружена | `ToolSearch("select:SendMessage,TaskStop")` |
| У `Agent` нет параметра `name` | Не задан `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` (или #100613) | Режим A невозможен — по таблице Preflight в SKILL.md |
| В результате спавна `name: tester-parser-2` вместо `tester-parser` | Имя занято живым тиммейтом | `TaskStop` нового; выяснить, почему жив старый (не остановлен? воскрешён?), остановить его; спавн под следующим `-r<n>` |
| Остановленный этап снова работает и помнит старое | Кто-то написал на его имя — `SendMessage` воскресил старый инстанс | `TaskStop` ещё раз; остановленным именам не писать; следующий спавн — под новым именем |
| Тиммейт молчит, отчёта нет | Ждёт ввода; сообщение припарковалось на переходе в idle; висит на permission-промпте | Прочитать `result` последнего idle-уведомления; короткий пинг; сказать пользователю про промпт; не помогло — `TaskStop` и спавн `-r<n>` |
| Один отчёт пришёл 2–4 раза или старый всплыл после компакта | #92244, #97798 | Идемпотентно: этап не перезапускать; дубль от остановленного этапа игнорировать |
| Поправка дошла, когда работа уже сделана | Сообщение занятому тиммейту доставляется после конца хода (#99111) | `TaskStop` и спавн `-r<n>` с исправленным брифом |
| `CLAUDE_CODE_ENTRYPOINT` — `sdk-cli` / `sdk-*` | Неинтерактивная сессия (`-p`, SDK): `name` есть, но тиммейтов не будет | Режим A невозможен — по таблице Preflight в SKILL.md |
| После `/resume` отчёты не приходят | In-process тиммейты не пережили resume (#100013) | Респавн текущего этапа под новым именем |
| Тиммейт получает `team-swarm isolation: … no recognisable scope` | Рекурсивный поиск или `git diff` без пути с `/` (`rg x src` вместо `rg x src/`) | Ничего не править: текст отказа говорит перезапустить со своей папкой через `/` |
| Тиммейт получает `team-swarm isolation: … may not access …` на нужный ему файл | Путь в карте `.team-swarm/isolation.json` шире, чем надо, или файл объявлений не вынесен в исключение | Поправь карту (`"!<путь>"` — исключение для Read/Edit/Grep, не для Bash); гард перечитывает её на каждый вызов |
| Тиммейт не видит MCP-инструментов | Заспавнен в первом ходе сессии, пока MCP подключался (#98953) | `TaskStop`, спавн `-r<n>` из следующего хода |
