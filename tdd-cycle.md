# TDD Cycle — runbook для лида

Лид использует этот документ как пошаговый гайд по ведению фичи через TDD в swarm mode. API-детали (имена, `TaskStop`, доставка сообщений) — в `swarm-primitives.md`.

Содержание:
- Инициализация сессии
- Для каждой фичи: имена и смена этапа · RED · GREEN (+ REFACTOR) · REVIEW · пока этап идёт
- Завершение сессии
- Правила переформулировки фидбека — правила и три примера
- Признаки нарушения изоляции
- Error handling

## Инициализация сессии

Перед первой фичей:

0. Preflight по разделу «Требования среды и Preflight-гейт» в SKILL.md: параметр `name` в схеме `Agent`, `echo $CLAUDE_CODE_ENTRYPOINT` не `sdk-*` (интерактивная сессия), `ToolSearch("select:SendMessage,TaskStop")`, `Workflow`. Строка `Preflight: Agent(name) ✅ · cli ✅ · SendMessage ✅ · Workflow ✅ → режим A (TDD), agent-teams` — в первом сообщении пользователю после входа в скилл, при любом исходе. При провале — решение по таблице оттуда же; команду не изображать и в соло молча не уходить.
1. Оценить, нужна ли вообще команда (раздел «Оценка перед формированием команды» в SKILL.md). Тривиальная задача — сказать об этом одной строкой и сделать соло. Средняя — объявить дефолт и действовать в том же ходе («Средняя задача — собираю команду; скажи "соло", если хочешь иначе»). Сложная или пользователь явно просил — дальше по пунктам.
2. Имя команды — slug из описания задачи (`"напиши CLI-калькулятор"` → `"cli-calculator"`) или имя от пользователя. Это метка для плана, в API не участвует; подтверждения не спрашивать.
3. Рекомендованные плагины (`compound-engineering`, на фронтенде `impeccable`; `superpowers` — фолбек, его не предлагать): если какого-то нет, а задача от него выиграет, — одна строка рядом с планом (что даёт, как поставить), без вопроса, и работа идёт дальше. См. «Рекомендованные плагины» в SKILL.md.
4. Команду создавать не нужно — сессия уже неявная команда; сразу к декомпозиции, спекам и спавну.
5. Декомпозировать задачу в фичи — в план лида, один пункт на фичу. План держи у себя: в контексте, для длинной работы — в файле плана проекта. `feature-id` — короткий slug: он войдёт в имена тиммейтов.
6. Написать спеки. Для каждой фичи — `specs/<feature-id>.md` с разделами:
   - Назначение (один абзац).
   - API (модуль / путь импорта и сигнатуры публичного интерфейса — tester берёт их отсюда, `src/` он не видит).
   - Контракт (входы, выходы, ошибки).
   - Edge cases.
   - Инварианты.
   - Примеры (вход → выход, на уровне поведения).
7. Создать skeleton публичного интерфейса в `src/` — сигнатуры + заглушка (`raise NotImplementedError("stub")` или проектный эквивалент). Сигнатуры tester'у даёт раздел API спеки, а не этот файл.
7a. Записать карту изоляции для гарда: `mkdir -p .team-swarm && printf '*\n' > .team-swarm/.gitignore` и `.team-swarm/isolation.json` вида `{"tester": ["src/"], "developer": ["tests/"]}` с путями проекта (синтаксис — SKILL.md → «Режим A: TDD-цикл»). Без карты гард блокирует тиммейтам только `Agent` / `TaskStop`, пути держат лишь брифы.
8. Опубликовать план пользователю и стартовать в том же ходе. Подтверждения не ждём: вопрос в CLI заканчивает ход и останавливает работу. Спрашивать стоит, только если разные трактовки задачи ведут к существенно разной работе.

## Для каждой фичи

### Имена и смена этапа

Respawn-per-stage: на каждый этап (RED, GREEN, REVIEW) — новый тиммейт с чистым контекстом. Причина — изоляция: tester не несёт знание о тестах в реализацию, developer прошлого раунда не тащит старые догадки, а reviewer смотрит без истории рождения решения. Цена честная: каждый спавн заново собирает контекст (спеку, интерфейс, файлы). Итерации внутри этапа (раунды на падающих тестах, refactor) ведёт тот же живой тиммейт.

Имена этапов уникальны и не переиспользуются:
- `tester-<feature-id>`, `developer-<feature-id>`, `reviewer-<feature-id>`;
- повторный спавн той же роли на той же фиче — `-r2`, `-r3` (следующий свободный номер): после REJECT, после поправки посреди этапа, после падения тиммейта.

**Смена этапа идёт в порядке «финальный отчёт → `TaskStop` старого → спавн следующего», и остановленному этапу лид больше не пишет: сообщение на его имя воскресит старый инстанс со всем старым контекстом.**

После каждого спавна сверь `name:` в результате `Agent` с запрошенным; не совпало — `TaskStop` нового и разберись, кто держит имя.

Назначение задачи = спавн-бриф: все входные данные этапа (спека, файлы, команда тестов и сборки, замечания REJECT'а) подставляются в бриф при спавне. В последовательном TDD RED закрыт до старта GREEN, одновременно живых пиров нет: в брифе блок `{{peers}}` — вариант «none», tester и developer пишут только лиду (`"main"`), вопросы по спеке — тоже лиду, он её владелец.

Поправка посреди этапа. Сообщение занятому тиммейту доходит только после конца его хода (#99111), то есть когда работа уже сделана. Если курс надо сменить, пока этап идёт, — `TaskStop` и спавн с исправленным брифом под `-r<n>`, а не догоняющий `SendMessage`. `TaskStop` не флашит: несообщённое пропадёт, а записанное на диск останется — посмотри, что там, и опиши в новом брифе.

### RED (тесты должны упасть)

1. Отметить `"RED: <feature-id>"` в плане как in progress.
2. Спавн `tester-<feature-id>` через `Agent` с брифом из `role-briefs.md` (спека, `{{interface-files}}` — «none», путь для тестов, команда тестов, `{{peers}}` — «none»). Сверить имя. Tester прошлой фичи уже остановлен — спавним нового.
3. Дождаться отчёта (`SendMessage` на `"main"`, придёт сам): "RED done for <feature-id>: ...". Тиммейт ушёл в idle без отчёта — сначала прочитай `result` idle-уведомления.
4. Прогнать тесты (`pytest tests/` / проектный эквивалент; при работе внахлёст — только тесты этой фичи).
   - Все падают на заглушке → ✅ Red, дальше.
   - Какой-то проходит → подозрение: напиши `tester-<feature-id>`, попроси проверить. Это итерация внутри RED, тот же тиммейт.
   - Syntax/import error → попроси починить. Тоже внутри RED.
5. `TaskStop("tester-<feature-id>")` — после финального отчёта. Это имя больше не адресуем.

### GREEN (минимальная реализация)

6. Отметить `"GREEN: <feature-id>"` в плане.
7. Спавн `developer-<feature-id>` через `Agent` с брифом (спека, интерфейс, путь `src`, команда сборки, `{{peers}}` — «none»; команды тестов в брифе нет — тесты гоняет лид). Новый инстанс, чистый контекст. Сверить имя.
8. Дождаться отчёта: "GREEN done for <feature-id>: ...".
9. Прогнать тесты.
   - Все зелёные → шаг 11 (сначала стоп developer'а, потом REVIEW).
   - Падают → итерация внутри GREEN, developer остаётся жить:
     1. Прочитать вывод тестов.
     2. Переформулировать семантически (правила ниже).
     3. Отправить живому developer'у по имени его этапа: `SendMessage({ to: "developer-<feature-id>", summary: "feedback round N", message: "Feedback round N for <feature-id>: <суть одной строкой>\n<semantic feedback>" })`. Первая строка — самодостаточный заголовок: получатель видит её как превью, а `summary` ему не передаётся.
     4. Ждать новый отчёт, снова прогонять тесты.
10. Максимум 3 раунда. Если после 3 тесты всё ещё красные — эскалация:
    - Перечитать спеку — возможно, неполна или противоречива.
    - Сообщить пользователю: "developer не сходится за 3 раунда на фиче X. Вывод тестов: ..., последние фидбеки: ...".

### REFACTOR (опционально, внутри GREEN — до остановки developer'а)

Если всё зелёное, но код можно улучшить, — до шага 11 отправь `developer-<feature-id>`: "refactor for readability, extract helpers, no behavior change". Прогнать тесты после. Красные — откат или новая GREEN-итерация. Refactor — часть фазы GREEN, тот же developer, без респавна.

### Переход GREEN → REVIEW

11. `TaskStop("developer-<feature-id>")` — после последнего отчёта.

### REVIEW

12. Отметить `"REVIEW: <feature-id>"` в плане.
13. Спавн `reviewer-<feature-id>` — свежий тиммейт (`general-purpose` или агент compound-engineering без JSON-only вывода — см. SKILL.md → «Архитектура»), не форк: форк унёс бы рассуждения лида, а судье нужен взгляд со стороны. В бриф — спека, src- и test-файлы, вывод последнего прогона тестов и текущие имена для маршрутизации замечаний (`{{route-names}}`: `developer-<feature-id>`, `tester-<feature-id>` с номером раунда, если он был). Вывод тестов клади прямо в бриф: сообщение, отправленное сразу после спавна, дойдёт только после конца первого хода reviewer'а — скорее всего, уже после вердикта.
14. Дождаться вердикта.

Планка REJECT: нарушение спеки или контракта; баг, дающий неверное поведение; нарушение изоляции; правка вне скоупа. Остальное reviewer пишет в «Minor notes» — они фичу не блокируют.

`APPROVE` → `TaskStop("reviewer-<feature-id>")` → закрыть фичу в плане → следующая фича (новый `tester-<next-id>`). Minor notes — в финальный отчёт или отдельной правкой. Фронтенд-задача — сначала дизайн-проход `impeccable` (раздел в SKILL.md).

`REJECT` → `TaskStop("reviewer-<feature-id>")`, затем маршрут по тегам замечаний (reviewer ставит в тег имя этапа из брифа или `lead`). Прежним tester'у и developer'у не пишем, даже если «он же помнит код»: сообщение вернёт его со старым контекстом. Вместо этого — новый спавн с замечаниями в брифе. Перед вставкой переформулируй их по правилам ниже («Правила переформулировки фидбека»): developer'у — без имён тестов, путей в `tests/` и ожидаемых значений, tester'у — без путей в `src/` и деталей реализации; строка Evidence остаётся у лида.
- `[to: developer-…]` → `developer-<feature-id>-r2` (дальше `-r3`) с замечаниями REJECT'а. Цикл GREEN повторяется.
- `[to: tester-…]` → `tester-<feature-id>-r2` с замечаниями и командой тестов без трейсбеков (pytest: `--tb=no -q`): реализация уже не заглушка, а трейсбек печатает её исходник. После — обычно нужен новый GREEN (код может развалиться) и новый REVIEW, тоже со следующими номерами.
- `[to: lead]` → пересмотреть спеку или архитектуру, обновить `specs/<feature-id>.md`, вернуться к RED с новыми спавнами.

После правок — свежий `reviewer-<feature-id>-r2` на повторный REVIEW. Максимум 3 цикла ревью, дальше — эскалация пользователю.

### Пока этап идёт

Лид не ждёт впустую, пока тиммейт работает: готовит следующую фичу — спеку и skeleton. Дефолт — фичи последовательно. Если фичи независимы (их файлы в `src/` и `tests/` не пересекаются), их можно вести внахлёст: RED фичи B во время GREEN фичи A. Тогда:
- `tester-b` и `developer-a` пирами друг другу не становятся — работают над разными фичами, в брифах по-прежнему `{{peers}}` — «none»;
- тесты гоняй по фиче, а не весь `tests/`: иначе красный RED фичи B покрасит прогон фичи A;
- смена этапа и имена — для каждой фичи свои, по правилам выше.

## Завершение сессии

Respawn-per-stage закрывает каждый этап `TaskStop`'ом, но idle-тиммейты сами не завершаются (#89515), а этап, случайно воскрешённый сообщением, снова висит фоном. Поэтому в конце: `ListAgents` → `TaskStop` каждого ещё живого тиммейта этого прогона. `ListAgents` показывает и соседние сессии машины — останавливай только имена своего прогона. Роспуск команды не нужен — она живёт с сессией. Карту изоляции убери: `rm -rf .team-swarm`.

Финальный отчёт пользователю: что сделано, какие файлы, пройденные ревью, известные ограничения и фактическая цена прогона — сколько тиммейтов и этапов, сколько времени.

## Правила переформулировки фидбека (для шага 9.2 и замечаний REJECT)

Когда developer получает фидбек о падающих тестах — лид формулирует его семантически, не цитируя тесты.

### Правила
- Ссылайся на спеку, не на тесты. "По п. X контракта..." вместо "тест ждёт...".
- Описывай поведение, не значения. "Неправильно обрабатывается пустой вход" вместо "должно быть []".
- Не упоминай имена тестов. Никогда.
- Не цитируй значения из assertion'ов. Они могут работать как подсказки.
- Если не можешь переформулировать семантически — это сигнал, что спека неполная. Допиши спеку, потом формулируй.
- **Замечание для tester'а** (REJECT `[to: tester-…]`) — обратная сторона: без путей в `src/`, внутренних имён и деталей реализации; только какое требование спеки тесты оставляют непроверенным.

### Пример 1: деление на ноль

Сырой вывод (лид видит):
```
FAILED tests/test_calc.py::test_divide_by_zero_raises_value_error
AssertionError: Expected ValueError, got ZeroDivisionError
```

❌ Developer'у так нельзя:
> "Тест `test_divide_by_zero_raises_value_error` ждёт ValueError, получил ZeroDivisionError"

✅ Можно так:
> "По спецификации (п. 'Ошибки'), функция `divide` при невалидном делителе должна сигнализировать ошибкой на уровне API контракта, не пропуская наружу низкоуровневое арифметическое исключение."

### Пример 2: пустой вход

Сырой вывод:
```
FAILED tests/test_parser.py::test_empty_input_returns_empty_list
AssertionError: assert None == []
```

❌ Так нельзя:
> "Тест ждёт `[]`, а получает `None` на пустом входе"

✅ Можно:
> "По спеке (раздел Выходы) `parse` всегда возвращает список. Сейчас есть путь, где возвращается не список — проверь обработку граничного случая пустого входа."

### Пример 3: off-by-one

Сырой вывод:
```
FAILED tests/test_paginate.py::test_last_page_partial_fill
AssertionError: assert len(result.items) == 3, got 2
```

❌ Так нельзя:
> "На последней странице должно быть 3 элемента, а не 2"

✅ Можно:
> "В пагинации неверно рассчитывается количество элементов на последней странице для случая, когда общее число не делится нацело на размер страницы (edge case 'partial last page' в спеке). Проверь границы цикла."

## Признаки нарушения изоляции

### Developer подсмотрел тесты
- Захардкоженные значения, похожие на "правильные ответы" для конкретных кейсов.
- Код обрабатывает ровно те случаи, что в тестах, и падает на похожих.
- Магические числа, не объяснённые спекой.
- Имена переменных, echoing test names.

### Tester подсмотрел код
- Обращения к приватным функциям/атрибутам (`_helper`, `self._cache`).
- Assert'ы на внутреннюю структуру данных, не описанную в спеке.
- Mock внутренних зависимостей, невидимых через публичный API.
- Тесты ломаются от рефакторингов, не меняющих поведение.

При любом подобном признаке лид режектит сам, не дожидаясь reviewer'а. Сообщением это не лечится: прочитанное из контекста тиммейта не выкинуть, и результат этапа под подозрением. Поэтому — `TaskStop` этапа (если он ещё жив) и спавн той же роли под `-r<n>`, в брифе — что именно нарушено и что переделать. Остановленному этапу не пиши: вернётся вместе с подсмотренным.

## Error handling

### Тиммейт не отвечает
- Idle — норма, он ждёт ввода. Сначала прочитай `result` последнего idle-уведомления: там финальный текст его хода, иногда отчёт уже в нём.
- На follow-up пришло только idle-уведомление без реакции — сообщение могло припарковаться на переходе в idle (#82858): короткий пинг, а не весь бриф заново.
- Ни отчёта, ни idle — возможно, висит на permission-промпте: промпты тиммейтов всплывают в сессии лида и ждут пользователя, отдельного сигнала нет (#99887). Скажи пользователю, какой тиммейт ждёт разрешения.
- Явно упал или не будится — `TaskStop(<имя этапа>)` и спавн той же роли под `-r<n>` с тем же брифом плюс что уже сделано (сверь по диску: несообщённое `TaskStop` не сохраняет).

### Дубли отчётов
Один отчёт может прийти несколько раз, а старый — всплыть после компакта лида (#92244, #97798). Обрабатывай идемпотентно: повтор (тот же отправитель и timestamp или тот же текст) не перезапускает тесты, не спавнит следующий этап второй раз и не двигает счётчик раундов. На дубль от уже остановленного этапа не отвечай: ответ воскресит этап.

### Лид пережил /resume или рестарт
In-process тиммейты его не переживают, а их отправки после рестарта теряются (#100013). Определи по плану и диску, на каком этапе остановились, и заспавни этот этап заново под `-r<n>`.

### Conflicting verdicts / loops
- Reviewer REJECT → developer fix → REJECT по другим причинам → и так по кругу. Это сигнал проблем со спекой. Останови цикл, перечитай спеку, возможно — эскалация пользователю.

### Тиммейт пишет «spec is unclear»
- Это ожидаемое и правильное поведение: тиммейт делает то, что спека задаёт однозначно, и спрашивает только про неясную часть. Не заставляй его гадать. Допиши спеку и ответь живому тиммейту по имени его этапа через `SendMessage` — ответ дойдёт, когда он закончит текущий ход. Если уточнение меняет уже сделанную работу, — `TaskStop` и спавн `-r<n>` с обновлённой спекой в брифе.
