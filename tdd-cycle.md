# TDD Cycle — runbook для lead'а

Lead использует этот документ как пошаговый гайд по ведению фичи через TDD в swarm mode.

## Инициализация сессии

Перед первой фичей:

0. **Оценить, нужна ли вообще команда.** См. раздел «Оценка перед формированием команды» в SKILL.md. Если задача тривиальная — сказать пользователю честно и предложить сделать одному. Если средняя — упомянуть выбор. Если сложная или пользователь явно просил — продолжай дальше по пунктам.
1. **Preflight-гейт (ОБЯЗАТЕЛЬНО).** Выполнить по разделу «Требования среды и Preflight-гейт» в SKILL.md: живая проверка `Agent`/`SendMessage` (через `ToolSearch("select:SendMessage")`)/`Workflow`, **обязательная Preflight-строка в сообщении пользователю до первого спавна**, решение строго по таблице. Провал → СТОП и разговор с пользователем, никаких симуляций и молчаливого соло.
2. **Определить имя team'ы.** По умолчанию — slug из описания задачи (`"напиши CLI-калькулятор"` → `"cli-calculator"`). Если пользователь указал своё имя — использовать его. Подтверждение для дефолтного имени не запрашивать.
3. **Проверить наличие рекомендованных плагинов** (`superpowers`, `compound-engineering`). Если какой-то не установлен, а задача от него выиграет — в первом сообщении пользователю рядом с планом коротко упомянуть: что это, что даёт, как поставить, продолжать без или подождать. Не блокировать работу — продолжать без, если нет явного ответа. См. раздел «Рекомендованные плагины» в SKILL.md.
4. **Команду создавать не нужно** — сессия уже является неявной командой (implicit-team); сразу переходи к декомпозиции, спекам и спавну teammates через `Agent`.
5. **Декомпозировать задачу в фичи.** Записать в план лида — один пункт на фичу. Отдельного инструмента для плана нет: держи его у себя (в контексте, а для длинной работы — в файле плана проекта).
6. **Написать спеки.** Для каждой фичи — `specs/<feature-id>.md` с разделами:
   - Назначение (один абзац).
   - API (публичный интерфейс, сигнатуры).
   - Контракт (входы, выходы, ошибки).
   - Edge cases.
   - Инварианты.
   - Примеры (вход → выход, на уровне поведения).
7. **Создать skeleton публичного интерфейса** в `src/` — сигнатуры + `raise NotImplementedError("stub")`.
8. **Опубликовать план пользователю** и получить подтверждение, если план нетривиальный.

## Для каждой фичи

**Общий принцип: respawn-per-stage.** На каждый этап (RED, GREEN, REVIEW) — новый teammate с чистым контекстом. После завершения этапа — `TaskStop(<name>)`, и только тогда спавнить следующего. Итерации внутри одного этапа (например, несколько раундов на падающих тестах) — **без** respawn'а, это тот же teammate. Назначение задачи = спавн-промпт: все входные данные этапа (спека, файлы, замечания) подставляются в brief при спавне.

### RED (тесты должны упасть)

1. Отметить `"RED: <feature-id>"` в плане как in progress.
2. **Spawn tester** через `Agent` с brief'ом из `role-briefs.md` (плейсхолдеры: спека, интерфейсные файлы, путь для тестов). Даже если на предыдущих фичах tester уже был — он уже остановлен, спавним нового.
3. Дождаться отчёта tester'а (придёт автоматически новым ходом): "RED done, files: ..., coverage: ...".
4. Прогнать тесты (`pytest tests/` / проектный эквивалент).
   - Все падают с NotImplementedError → ✅ Red, дальше.
   - Какой-то проходит → подозрение: напиши tester'у, попроси проверить. Это итерация внутри RED — без respawn'а.
   - Syntax/import error → попроси починить. Тоже без respawn'а.
5. **`TaskStop("tester")`.** Tester'а больше нет.

### GREEN (минимальная реализация)

6. Отметить `"GREEN: <feature-id>"` в плане.
7. **Spawn developer** через `Agent` с brief'ом (плейсхолдеры: спека, интерфейс, путь src). Новый инстанс, чистый контекст.
8. Дождаться отчёта developer'а (придёт автоматически): "GREEN done, files: ...".
9. Прогнать тесты.
   - **Все зелёные** → переход к шагу 11 (сначала стоп developer'а, потом REVIEW).
   - **Падают** → итерация **внутри** GREEN (развёрнутый developer остаётся жить):
     1. Прочитать вывод тестов.
     2. **Переформулировать** семантически (правила ниже).
     3. Отправить developer'у: `SendMessage({ to: "developer", summary: "feedback on failing tests", message: "<semantic feedback>" })`.
     4. Ждать новый отчёт developer'а, снова прогонять тесты.
10. **Максимум 3 раунда.** Если после 3 тесты всё ещё красные — эскалация:
    - Перечитать спеку — возможно, неполна/противоречива.
    - Сообщить пользователю: "developer не сходится за 3 раунда на фиче X. Вывод тестов: ..., последние feedback'и: ...".

### REFACTOR (опционально, внутри GREEN — до остановки developer'а)

Если всё зелёное, но код можно улучшить — **до шага 11** отправь developer'у: "refactor for readability, extract helpers, no behavior change". Прогнать тесты после. Красные — откат или новая GREEN-итерация. Refactor — это часть фазы GREEN, того же developer'а, без respawn'а.

### Переход GREEN → REVIEW

11. **`TaskStop("developer")`.** Developer'а больше нет.

### REVIEW

12. Отметить `"REVIEW: <feature-id>"` в плане.
13. **Spawn reviewer.** Новый инстанс (плейсхолдеры: спека, src-файлы, test-файлы). Сразу отправь ему вывод последнего прогона тестов:
    ```
    SendMessage({ to: "reviewer", summary: "test run summary for <feature-id>", message: "Test run summary for <feature-id>: <pass/fail counts, full output>" })
    ```
14. Дождаться verdict (придёт автоматически).

**APPROVE** → `TaskStop("reviewer")` → следующая фича (возвращаемся к RED с новым spawn tester'а).

**REJECT** → `TaskStop("reviewer")`, затем по маршрутизации замечаний:
- `[to: developer]` → **новый spawn developer'а** (чистый контекст, замечания REJECT'а подставлены в brief). Цикл GREEN повторяется.
- `[to: tester]` → **новый spawn tester'а** с замечаниями в brief'е. После — обычно нужен новый GREEN (код может развалиться) и новый REVIEW.
- `[to: lead]` → пересмотреть спеку/архитектуру, обновить `specs/<feature-id>.md`, возврат к RED с новым spawn'ом.

**Максимум 3 цикла review.** После — эскалация пользователю.

### Завершение сессии

Поскольку respawn-per-stage гарантирует, что в конце каждого этапа сделан `TaskStop`, в конце сессии никого не висит. Роспуск команды не требуется — она живёт с сессией и исчезает вместе с ней.

Финальный отчёт пользователю: что сделано, какие файлы, пройденные review, известные ограничения.

**Если по какой-то причине teammate остался активным** — он висит фоном и тратит ресурсы. `TaskStop(<name>)` останавливает его принудительно, подтверждений не требуется.

## Правила переформулировки feedback'а (для шага 9.2)

Когда developer получает feedback о падающих тестах — lead формулирует его **семантически**, не цитируя тесты.

### Правила
- **Ссылайся на спеку, не на тесты.** "По п. X контракта..." вместо "тест ждёт...".
- **Описывай поведение, не значения.** "Неправильно обрабатывается пустой вход" вместо "должно быть []".
- **Не упоминай имена тестов.** Никогда.
- **Не цитируй значения из assertion'ов.** Они могут работать как подсказки.
- **Если не можешь переформулировать семантически** — это сигнал, что спека неполная. Допиши спеку, потом формулируй.

### Пример 1: деление на ноль

Сырой вывод (lead видит):
```
FAILED tests/test_calc.py::test_divide_by_zero_raises_value_error
AssertionError: Expected ValueError, got ZeroDivisionError
```

❌ Developer'у так НЕЛЬЗЯ:
> "Тест `test_divide_by_zero_raises_value_error` ждёт ValueError, получил ZeroDivisionError"

✅ Можно так:
> "По спецификации (п. 'Ошибки'), функция `divide` при невалидном делителе должна сигнализировать ошибкой на уровне API контракта, не пропуская наружу низкоуровневое арифметическое исключение."

### Пример 2: пустой вход

Сырой вывод:
```
FAILED tests/test_parser.py::test_empty_input_returns_empty_list
AssertionError: assert None == []
```

❌ Так НЕЛЬЗЯ:
> "Тест ждёт `[]`, а получает `None` на пустом входе"

✅ Можно:
> "По спеке (раздел Выходы) `parse` всегда возвращает список. Сейчас есть путь, где возвращается не список — проверь обработку граничного случая пустого входа."

### Пример 3: off-by-one

Сырой вывод:
```
FAILED tests/test_paginate.py::test_last_page_partial_fill
AssertionError: assert len(result.items) == 3, got 2
```

❌ Так НЕЛЬЗЯ:
> "На последней странице должно быть 3 элемента, а не 2"

✅ Можно:
> "В пагинации неверно рассчитывается количество элементов на последней странице для случая, когда общее число не делится нацело на размер страницы (edge case 'partial last page' в спеке). Проверь границы цикла."

## Признаки нарушения изоляции

### Developer подсмотрел тесты
- Захардкоженные значения, похожие на "правильные ответы" для конкретных кейсов.
- Код обрабатывает ровно те случаи, что в тестах, и падает на похожих.
- Магические числа, не объяснённые спекой.
- Имена переменных, echoing test names.

### Tester подсмотрел код
- Обращения к приватным функциям/атрибутам (`_helper`, `self._cache`).
- Assert'ы на внутреннюю структуру данных, не описанную в спеке.
- Mock внутренних зависимостей, невидимых через публичный API.
- Тесты ломаются от рефакторингов, не меняющих поведение.

Lead при любом подобном признаке — сам режектит, не ждёт reviewer'а. Отправляет роли замечание через `SendMessage` с указанием, что исправить.

## Error handling

### Teammate не отвечает
- Idle — норма, он ждёт ввода: `SendMessage` разбудит. Если разбудить не удаётся или он явно упал — `TaskStop(<name>)` и respawn с тем же brief'ом (плюс контекст, что уже сделано).

### Conflicting verdicts / loops
- Reviewer REJECT → developer fix → REJECT по другим причинам → и так по кругу. Это сигнал проблем со спекой. Останови цикл, перечитай спеку, возможно — эскалация пользователю.

### Teammate says "spec is unclear"
- Это ожидаемое и правильное поведение. Не заставляй teammate'а гадать. Допиши спеку, отправь обновление через `SendMessage`.
